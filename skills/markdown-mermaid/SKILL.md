# Markdownとmermaidの書き方と表示の罠

Markdownとmermaidは、表示する環境（レンダラ）ごとに解釈が少しずつ違う。ある環境で正しく見えても、別の環境で崩れることがある。

- **基準**: 文書が読まれる環境（GitHub、VS Codeのプレビュー、社内のWiki等）を想定し、その中で最も厳しい解釈に合わせて書く。
- **1つの環境で確かめない**: 1つの環境で正しく見えたことを、他の環境でも正しい根拠にしない。
- **罠を見つけたら節を足す**: 書くことは、症状・原因・対策・確認した環境と日付。同じ種類の罠が他の文書にも無いか、機械的に探す（横展開）。

## 1. 図の記法の選び方（mermaidとSVG）

図表（フローチャート・状態遷移図等のダイアグラム）は、**基本的にmermaidを優先する**。SVGの手描きへの切り替えを検討するのは、状態・判定（ノード）の数がおおよそ10を超える規模になった場合を目安とする。

- mermaidの自動レイアウト（dagre）には、配線の折れ方や経路を明示的に指定する手段が原理的に無く、視認性を追い込めないことがある。
- SVGの手描きは、座標を1つずつ設計するため、mermaidより描画に要するトークンが大きく増える。
- 目安の件数に近い場合や迷う場合は、コストとのトレードオフになるので、ユーザーに確認してから決める。
- 座標を手描きする場合の設計指針は、`svg-diagram` エージェント定義を参照する（ここでは重複させない）。

## 2. 文中の数式は、全角の文字の直後から始めない

**症状**: 文中の数式が、GitHubでは記号のまま表示される。VS Codeのプレビューでは数式になる。

- 例: `$u_a$・$u_b$ は…` の `$u_b$`、`アクセル（$u_a = u$）` の `$u_a = u$`。
- 確認した環境: 2026-09-27、GitHub（複数のブラウザ）。

**原因**: GitHubは、数式の始まりの `$` のすぐ前が全角の文字（`・`・`（`・`。`・かな・漢字等）だと、数式として扱わない。

- 終わりの `$` の後に全角の文字が続くのは問題ない（`$u_a$・` は数式になる）。
- 前が半角スペース・行頭・表の区切りなら、数式になる。
- 独立した数式（`$$…$$`）は、この影響を受けない。
- VS Codeのプレビューは判定が緩いので、VS Codeで正しく見えても根拠にならない。

**対策**: 始まりの `$` の前に半角スペースを入れる。

```markdown
- $u_a$・ $u_b$ はアクセル・ブレーキの踏み込み。正ならアクセル（ $u_a = u$）とする。
```

GitHub独自の `` $`u_b`$ `` という書き方でもGitHubでは数式になる。ただし、VS Codeのプレビュー等では数式にならないおそれがあるので、複数の環境で読む文書では使わない。

**横展開**: 同じ形を機械的に探す。コードブロックの中とコードスパン（`` `…` ``）は数式にならないので、対象から外す。Pythonで探す例（ファイルに保存し、Windowsでは `py -3.13 find_math.py`、WSL/Linuxでは `python3 find_math.py` で実行する。素の `python` は使わない。`**/*.md` はカレントディレクトリ以下をすべて探すので、`node_modules` 等がある場合は対象を絞る）:

```python
import re, glob
for p in glob.glob('**/*.md', recursive=True):
    fence = False
    for i, l in enumerate(open(p, encoding='utf-8'), 1):
        if l.lstrip().startswith('```'):
            fence = not fence
            continue
        if fence or '$$' in l:
            continue
        t = re.sub(r'`[^`]*`', lambda m: ' ' * len(m.group()), l)
        for m in re.finditer(r'(?<!\$)\$(?=\S)([^$\n]+?)(?<=\S)\$', t):
            if m.start() > 0 and ord(t[m.start() - 1]) > 127:
                print(f'{p}:{i}: {t[max(0, m.start() - 3):m.end()].strip()}')
```

見つかった位置の `$` の前に、半角スペースを入れる。一括で直すなら、行の後ろの位置から順に挿入すると、位置がずれない。

## 3. mermaidのラベルを「1. 」で始めない

**症状**: ノードのラベルを `"1. フェーズ0"` のように「数字＋ピリオド＋空白」で始めると、「Unsupported markdown: list」と表示されることがある。この症状は実際の表示では確かめていない（2026-09-25に、mermaid v10以降の既知の挙動を避ける予防策として `【1】` の形にした。表示を確かめたら、確認した環境と日付に書き改める）。

**原因**: mermaid v10以降は、ラベルの中身をMarkdownとして解釈することがある。そのため、ラベルが番号付きリストと見なされる。mermaidの版が新しい環境ならどこでも起こりうる。

**対策**: 番号は `【1】` のように括弧で囲んで書く。

- 表の番号と対応させたいときも、最初からこの形で書く。
- `sed` 等で一括で置き換えるときは、1行に複数のノードがある場合に備えて `g` フラグを付ける。または、置き換えた後に全部の番号を数え直す。1行に2つあるノードの片方だけ、置き換えが漏れた前例がある。

## 4. VS Codeのプレビューで、mermaidを含む文書が崩れる

**症状と前例**: VS Codeの拡張機能「Mermaid」（publisher: MermaidChart。AI機能・クラウド連携付き）が、他のMarkdownの表示処理と競合して、プレビューの表示が崩れた前例がある。

**対策**: mermaidを含むMarkdownのプレビューが崩れる場合は、まずこの拡張の関与を疑う。この拡張を無効にしたうえで、`bierner.markdown-mermaid`（Markdown Preview Mermaid Support）を使う。

- AI機能付きの拡張は外部と通信しうるので、セキュリティの面でも使う理由が無い。
- 拡張の導入・無効化はユーザーが行い、Claudeは手順の案内までとする。

## 5. 数式の中で `\,` などの「`\` ＋記号」を使わない

**症状**: 数式の `c\,v`（細いすき間を空けた積）が、GitHubでは「c,v」とコンマ付きで表示される。依存関係や2つの量の列挙に見え、意味が変わる。VS Codeのプレビューでは正しく表示される。

- 確認した環境: 2026-10-05、GitHubの変換API（`gh api markdown`）。文中の数式（`$…$`）・表の中・独立した数式（`$$…$$`）のどれでも、返るHTMLの中で `c\,v` が `c,v` になっていた。

**原因**: GitHubは、数式として描く前に、Markdownの規則で「`\` ＋ASCIIの記号」を記号そのものに変える（`\,` → `,`）。`\ `（`\` ＋半角スペース）や、`\int`・`\Delta` のような「`\` ＋英字」は、そのまま残る（ここまでが確認した内容）。`\;`・`\!`・`\{`・`\}`・`\$` 等も、同じ規則で `\` が消え、`\\` は `\` が1つになると考えられる（Markdownの規則からの推定で、表示は未確認。確かめたら、確認した環境と日付に書き改める）。

**対策**: 数式の中で「`\` ＋記号」を使わない。

- 積は文字を並べるだけにする（`c v`、`K_p e`、`v \Delta t`）。数式の書き方として最も一般的で、空白は表示に影響しない。
- すき間がどうしても要るところ（積分の `e\ dt` 等）は、`\ ` を使う。
- GitHub独自の `` $`…`$ `` や ` ```math ` のブロックなら `\` は残るが、2節と同じ理由で、複数の環境で読む文書では使わない。

**横展開**: `grep -rn --include='*.md' '\\[][!"#$%&()*+,./:;<=>?@^_{|}~-]' .` のように、カレントディレクトリ以下のすべてのMarkdownから「`\` ＋記号」を探し（`'` と `` ` `` は探す記号から外している。`node_modules` 等がある場合は対象を絞る）、数式の中にあるものだけを直す（コードスパン・コードブロックの中のパス等は対象外）。

## 6. 数式の中で `*` を使わない

**症状**: 同じ段落に `$u^*$ … $u^* = …$` のように `*` を含む数式が2つ以上あると、GitHubで数式が崩れ、その間の文が斜体のように表示される。

- 確認した環境: 2026-10-09、GitHubの表示でユーザーが崩れを見つけた（ROS2の学習資料の、上付きの星 `u^*` を使う段落）。変換API（7節）では確かめていない。

**原因**: `*` が、数式として描かれる前に、Markdownの強調（斜体・太字）の記号として解釈されたと考えられる（表示からの推定）。5節の「`\` ＋記号」と同じく、GitHubでは、数式の中身がMarkdownの処理から守られないことがある。

**対策**: 数式の中で `*` を書かない。

- 上付きの星は `u^{\ast}` と書く（表示は `u^*` と同じ）。
- 掛け算は、文字を並べる（5節）か `\times` を使う。
- 数式の外で、元の表記をそのまま見せたいとき（ユーザーの言葉の引用など）は、コードスパン（`` `$u^*$` ``）にする。

**横展開**: コードブロックとコードスパンを除いて、文中の数式（`$…$`）の中に `*` が無いかを、短いスクリプトで機械的に探す。正規表現の `grep` だけでは、数式の範囲を正しく切り出しにくい。

## 7. 表示の確かめ方

- **GitHub**: GitHubのMarkdown変換APIに文書を送ると、GitHubが生成するHTMLが返る。PowerShellでも同じコマンドで動く（`gh` が導入・認証済みであること。未導入なら、導入はユーザーに委ねる）。ただし、Windows PowerShell 5.1の `>` はUTF-16LEで書き出すので、そのまま検索すると判定を誤るおそれがある。PowerShellでは `| Out-File -Encoding utf8 out.html` で書き出すか、変数に受けて調べる（`powershell-scripting` スキルの文字コードの罠と同じ種類）。なお、PowerShell 5.1は `gh` の出力をコンソールの文字コード（日本語の環境ではcp932）で読み込むため、HTMLの中の日本語は化けることがある。判定に使う `$` とタグ（`<math-renderer>`・`<pre>`・`<code>`）はASCIIなので、判定には影響しない。

  ```bash
  gh api markdown -f mode=gfm -F text=@docs/example.md > out.html
  ```

  - 数式として認識された部分は、`<math-renderer>` の要素になる。`<math-renderer>`・`<pre>`・`<code>` の中を除いて `$` が残っていなければ、文中の数式はすべて認識されている。
  - mermaidのブロックは、ブラウザ側で描かれる。そのため、このAPIでは描けるかどうかまでは分からない。
  - **送る内容に注意**: 本文がGitHubのAPIに送られる。公開済み、または公開してよい文書だけを送る。認証情報・個人情報・非公開のメモを含む文書は送らない。送る前に、目的と送る範囲をユーザー向けに説明し、承認を得てから送る。
- **VS Codeのプレビュー**: 判定が緩く、入れている拡張機能によって表示が変わる。VS Codeで正しく見えることは、他の環境で正しい根拠にならない。
- **mermaidの図**: 描画のためのツール（mermaid-cli等）は、新しいツールの導入に当たる。無断で入れない。基本は、書く時点で上の罠を避け、見た目の確認はユーザーに頼む。
- **見た目**: 最終的な見た目（数式の中身が正しく描かれるか、図の配置等）は、読まれる環境のブラウザ・アプリで確かめる。確認はユーザーに頼む。
