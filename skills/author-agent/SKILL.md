# サブエージェント定義の作成ガイド

Claude Codeのサブエージェント（`Agent`ツールで`subagent_type`として呼び出す、`.claude/agents/*.md`または`~/.claude/agents/*.md`に置くMarkdownファイル）を設計・作成するための汎用スキル。言語・プロジェクトを問わず適用できる。

## このスキルを使う場面

1. 新しいサブエージェントを一から設計するとき
2. 既存のagent定義ファイルをレビュー・改善するとき
3. 複数プロジェクトで使い回す前提の汎用エージェントを作り、保存先を`~/.claude/agents/`にすべきか判断するとき

## 個別エージェント作成時の必須確認事項（着手前）

実際に1体のエージェントを新規作成するときは、設計を進める前に次の4項目を**ユーザーに確認する**（こちらで推測して埋めない）。`AskUserQuestion`でまとめて聞くか、対話で順に確認する。

1. **名前** — `name`の元になる。こちらから候補を提案してよいが、最終的にユーザーの確認を得る
2. **目的** — 何をするエージェントか、いつ・何のために呼ぶか（`description`の元になる。「設計の4ステップ」1に対応）
3. **権限** — 次の4分類それぞれについて許可するかを確認する（`tools`/`disallowedTools`/`model`/`permissionMode`の元になる。「設計の4ステップ」3に対応）
   - **実行コマンド**（`Bash`） — シェルコマンド・ビルド・テスト実行等を行わせるか
   - **ファイル編集**（`Edit`/`Write`） — ファイルの作成・変更を行わせるか
   - **Git操作** — git関連コマンドの実行を行わせるか。行わせる場合も、`git-conventions`スキルが定める禁止操作（merge/rebase/amend/`reset --hard`/force push等）は既定で維持する（このエージェント固有に緩めない）
   - **サブエージェントの呼び出し**（`Agent`） — 他のサブエージェントを呼び出させるか。呼び出させる場合、呼び出せる対象を特定のagentに絞るか（`Agent(worker, researcher)`等）
   - **指定がない項目のデフォルト**: ユーザーが特に指定しなかった分類は、`tools`/`disallowedTools`でその分類を個別に制限せず、**通常のClaude Codeと同じ判断**に委ねる。すなわちツール自体は継続して使用可能にした上で、実行するかどうかは都度そのセッションの標準的な安全判断（破壊的操作・不可逆操作は事前確認する等、システムプロンプト冒頭の「Executing actions with care」に準じる判断）に従わせる。`permissionMode: bypassPermissions`のような確認省略は、ユーザーが明示的に指定しない限り設定しない
4. **性格** — 応答のトーン・振る舞いのスタンス（例: 厳格に指摘する／助言的、簡潔／詳細、迷ったら止まって確認する／自律的に進める 等）。システムプロンプトの語り口・判断のデフォルトスタンスに反映する。決め方の詳細は`references/description_and_prompt_writing.md`の「性格（トーン）の設計」を参照

ユーザーが即答できない項目は、このスキルの他章（保存場所の判断・tools権限の絞り込み・暴走防止）を踏まえた選択肢を提示し、選んでもらう。4項目が確定してから、以下の設計ステップと定義ファイルの作成に進む。

## 既存エージェントレビュー時の必須確認事項（着手前）

既存のagent定義ファイルをレビュー・改善するときは、レビューに着手する前に次の2点を**ユーザーに確認する**（こちらで対象や観点を推測して進めない）。`AskUserQuestion`でまとめて聞く。

1. **対象ファイル** — どのagent定義をレビューするか。`.claude/agents/`と`~/.claude/agents/`の両方から候補を列挙し、選んでもらう（複数選択可）
2. **レビュー観点** — 何を重視してレビューするか。少なくとも次を選択肢として提示する（複数選択可、自由記述も可）
   - 権限設計の妥当性（`tools`/`disallowedTools`/`permissionMode`が最小権限か、過不足がないか）
   - description文の精度（オーケストレーターが自動委任を正しく判断できる書き方か）
   - 暴走防止・曖昧さ排除（実行可否の明示、異常系・網羅的自動検証を許可していないか等）
   - frontmatterスキーマ準拠（`name`命名規則・必須項目・valid値など形式面の不備がないか）

ユーザーが「全部」「任せる」と答えた場合は、上記4観点すべてを既定の優先順位（権限設計→description文→暴走防止→スキーマ準拠）でカバーする。観点が確定してから読み込み・指摘出しに進み、指摘はユーザーが選んだ観点を優先して構成する。

## 設計の4ステップ

1. **目的とトリガーの明確化** — このエージェントは何をするためのものか。いつ（どんな依頼・状況で）呼ばれるべきか。単一責務に絞れているか（「何でも屋」は`description`が曖昧になり自動委任が機能しにくい）
2. **スコープと保存場所の決定** — このプロジェクト固有か、複数プロジェクトで使う汎用エージェントか。判断基準は「保存場所」章を参照
3. **権限設計** — `tools`/`disallowedTools`/`permissionMode`/`model`を最小権限の原則で決める。詳細は`references/frontmatter_reference.md`
4. **プロンプト本文の設計** — 役割・入出力・境界・報告形式・性格（トーン）を明記する。特に「実行してよいか、静的確認に留めるか」「異常系・網羅的自動化まで許すか」を曖昧にしない。詳細は`references/description_and_prompt_writing.md`と`references/antipatterns.md`

## frontmatterスキーマ（概要）

```yaml
---
name: string              # 必須。小文字+ハイフンのみ、コロン不可（コロンはplugin:subagent形式の予約）
description: string       # 必須。オーケストレーターが自動委任の可否を判断する文言
model: string              # 省略可: sonnet|opus|haiku|fable|full-model-id|inherit（デフォルトinherit）
tools: a, b, c             # 省略可: 許可ツールのallowlist。省略時は全ツール継承
disallowedTools: a, b      # 省略可: 継承ツールからの除外denylist
permissionMode: string     # 省略可: default|acceptEdits|auto|dontAsk|bypassPermissions|plan
skills: a, b                # 省略可: 使わせたいSkillを限定する場合
mcpServers: a, b            # 省略可
memory: user|project|local  # 省略可
maxTurns: integer           # 省略可
isolation: worktree         # 省略可: gitワークツリー隔離
color: string                # 省略可: タスク一覧での表示色
---
[システムプロンプト本文（Markdown）]
```

`name`/`description`必須、YAML不正やこの2項目欠落のファイルは黙ってスキップされる点に注意。フィールドの詳細な意味・制約（サブエージェントのネスト深さ上限、同時実行数上限など）は`references/frontmatter_reference.md`を参照。

## description文の書き方の要点

- オーケストレーターは**この文言だけ**を見て自動委任するかを判断する。曖昧な一言（例:「コードを見る」）ではなく、**いつ・何のために**呼ぶかを具体的・行動指向で書く
- 自動的な（プロアクティブな）呼び出しを促したい場合は「proactively」等のキーワードを含める
- 詳細な言い回しのコツ・悪い例/良い例は`references/description_and_prompt_writing.md`を参照

## tools権限とモデルの絞り込み

- 読み取り専用の調査エージェントには`Read, Grep, Glob`等の閲覧系のみを許可し、`Edit`/`Write`/`Bash`は与えない
- 破壊的操作をさせたくない場合は`disallowedTools`で明示的に除外する
- Git操作を許可する場合も、`git-conventions`スキルの禁止操作（merge/rebase/amend/`reset --hard`/force push等）はこのエージェント固有に緩めない。個別エージェントの本文で緩和・上書きしない
- サブエージェントの呼び出し（`Agent`）を許可する場合、無制限に任意のagentを呼べる状態にするか、`Agent(worker, researcher)`のように呼び出せる対象を絞るかを検討する
- `permissionMode: bypassPermissions`は、ユーザーから明示的な合意がある場合に限って使う。安易に設定すると承認プロンプトなしに高リスク操作が実行され得る。ユーザーが権限について指定しなかった分類は、この設定を追加せず通常のClaude Codeと同じ承認フローに委ねる（「個別エージェント作成時の必須確認事項」参照）
- モデルは迷ったら`inherit`のままにする。判断力・曖昧さの処理が必要なタスクは強いモデル、定型作業を大量にこなすタスクは軽いモデルが向く

## 暴走防止・曖昧さ排除（重要）

過去のプロジェクト運用（`waterfall-dev-workflow`スキル・関連CLAUDE.md）で実際に問題になった2パターンを、エージェント定義でも踏襲する。

- **実行可否の曖昧さ**: 「レビューして」とだけ書くと、意図しないコード実行（テスト起動等）が発生し得る。「静的レビューのみ（実行しない）」か「実行してよい」かをプロンプト本文に明示する
- **検証範囲の無限定によるツール呼び出し暴走**: 特にGUI/UI操作系のタスクで「厳密な自動検証」を指示すると、検証手段を粘り強く探し続けて長時間・大量のツール呼び出しに陥るリスクがある。正常系の最小限操作のみ許可し、異常系・網羅的自動化・スクリーンショット比較等の厳密な自動検証は行わせない旨と、目安のツール呼び出し回数を明示する

具体的な言い回しのテンプレートは`references/antipatterns.md`を参照。

## 保存場所の判断

- **`~/.claude/agents/`**（ユーザーレベル）: このマシン全体・複数プロジェクトで使い回す汎用エージェント
- **`<project>/.claude/agents/`**（プロジェクトレベル）: 特定プロジェクトのワークフローに紐づき、バージョン管理でチーム共有したいエージェント
- **プラグインの`agents/`**: 配布物として提供する場合（優先度は最も低く、`hooks`/`mcpServers`/`permissionMode`は非対応）
- 同名が複数スコープに存在する場合はファイルシステム順で解決されるため、汎用エージェントと同名のプロジェクト固有版を作らない（意図せず片方が隠れる）

## テンプレートと検証

- コピペで使える骨組みは`references/agent_template.md`を参照（読み取り専用調査系・静的レビュー系の2パターンを収録）
- 作成後は簡単なタスクで試し呼びし、(1)`description`だけで意図通りに自動委任されるか、(2)権限が過不足ないか、(3)暴走防止の言い回しが効いているかを確認する

## 他スキルとの関係

このスキルはエージェント**定義ファイルそのもの**の書き方に特化する。「どの工程でどのエージェントを呼ぶか」「レビュー往復を何回まで自動化するか」といった運用ルールは、`waterfall-dev-workflow`のようなプロジェクト固有のワークフロースキル側の管轄であり、本スキルはそれらのワークフローから呼ばれるエージェント自体を作る際の下請けとして使う。
