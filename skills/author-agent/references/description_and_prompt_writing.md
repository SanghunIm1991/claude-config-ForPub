# description文とシステムプロンプト本文の書き方

## description文（自動委任の判断材料）

オーケストレーター（メイン会話）は、ユーザーの依頼を見たときに各エージェントの`description`だけを読んで「このエージェントに任せるべきか」を判断する。本文（システムプロンプト）は委任が決まった**後**にしか読まれない。したがって`description`の質が委任の精度をほぼ決める。

### 悪い例と良い例

- 悪い例: `description: コードをレビューするエージェント`
  - 何のコードを、いつ、どんな観点でレビューするのかが不明。他のレビュー系エージェントと区別がつかない
- 良い例: `description: 実装コードの変更後、正しさ・セキュリティ・保守性の観点でプロアクティブにレビューする。コードを書いた・編集した直後に使う。`
  - 「いつ」（コードを書いた・編集した直後）と「何を」（正しさ・セキュリティ・保守性）が明示され、「プロアクティブに」で自動呼び出しを促している

### チェックリスト

- [ ] **いつ**呼ばれるべきかが書かれているか（トリガーとなる状況・依頼の言い回し）
- [ ] **何を**するエージェントかが具体的か（曖昧な動詞「見る」「対応する」を避ける）
- [ ] 自動的な（ユーザーが名指ししなくても）呼び出しを期待する場合は「proactively」「積極的に」等のキーワードを含めているか
- [ ] 似た役割の既存エージェントと区別できる文言になっているか（重複すると誤って選ばれる／選ばれない揺れが生じる）
- [ ] 実行してよい操作の種類（静的確認のみ／実行を伴う）が`description`の時点で読み取れるか、少なくとも本文で明確になるか

## システムプロンプト本文

委任が決まった後、エージェントはこの本文だけを頼りに動く（呼び出し元の会話文脈は原則見えない）。以下を明記する。

1. **役割（1文で言えるか）** — 単一責務に絞る。「何でも屋」にすると本文が肥大化し、判断がぶれる
2. **入力として期待するもの** — 呼び出し元がプロンプトにどんな情報を含めるべきか（ファイルパス、対象範囲、背景など）。エージェント側の前提が呼び出し元に伝わっている必要がある
3. **出力・報告形式** — 自由記述でよいか、構造化（箇条書き・特定フォーマット）が必要か。呼び出し元が結果をどう使うかを踏まえる
4. **やってよいこと／やってはいけないこと（境界）** — スコープ外の操作（例: ファイルの削除、git push、他エージェントの呼び出し）を明示的に禁止する。tools権限で技術的に絞れない操作（例: 「読み取り専用ツールしか渡していないが念のため書き込み系の提案もしない」）はプロンプトの記述でも補強する
5. **判断に迷ったときの振る舞い** — 想定外の状況に遭遇したら止まって報告するのか、ベストエフォートで進めるのかを書いておくと、暴走や無限試行を防ぎやすい（`antipatterns.md`も参照）

## 性格（トーン）の設計

「性格」とは、エージェントの応答スタイル・振る舞いのデフォルトスタンスのこと。同じ役割・権限でも、性格の設定次第でユーザー体験が大きく変わる。新規エージェント作成時は、次の観点を確認し、システムプロンプト本文の文体・指示に反映する。

| 観点 | 選択肢の例 |
|---|---|
| 指摘・報告のトーン | 厳格に問題点を指摘する／助言的・提案ベースで伝える |
| 詳細度 | 簡潔に結論だけ／根拠や過程も詳しく書く |
| 判断に迷ったときの姿勢 | 止まってユーザーに確認する／ベストエフォートで自律的に進める（「境界」の記述と連動させる） |
| 一人称・口調 | である調／です・ます調、フランクさの度合い |
| 楽観度 | 問題を見つけたら率直に厳しく言う／まず良い点も添えてから指摘する |

決まった性格は、本文の「役割」節の文体そのものに反映するほか、必要なら明示的に一文を加える（例: 「指摘は率直に行い、曖昧な表現でぼかさないこと」「不明点は推測で進めず、必ず一度ユーザーに確認してから進めること」）。性格の設定は「境界」節（アンチパターン1: 実行可否の曖昧さ）や「判断に迷ったときの振る舞い」と矛盾しないようにする（例: 「自律的に進める」性格なのに境界節で「必ず確認を挟む」と書くと矛盾する）。

### 分量の目安

厳密な文字数上限はない。ただし本文が長大になるほど「結局何をするエージェントか」がぼやけやすいので、`description`のトリガーに直結する内容に絞り、汎用的な心構え論（一般的な良いコーディング作法など）は書かない。プロジェクト固有のルール（コミット規約・承認フロー等）はエージェント本文に書かず、プロジェクトの`CLAUDE.md`や専用スキル側に置き、エージェント本文からは「〇〇スキルに従う」と参照するに留める方が、エージェント定義の使い回し（他プロジェクトへの転用）がしやすい。
