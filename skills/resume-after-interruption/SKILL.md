# 異常終了セッションからの復旧・再開

前回セッションがトークン上限・強制終了・クラッシュ等で通常の終了フローを踏まずに切れた場合、
「作業は完了したとユーザー(または前回セッションの自分)が思っている」状態と「実際にディスク上・
Gitリポジトリ上にある状態」がずれている可能性がある。特に、実装・テストまで完了していても
`git commit`前に切れていると、次回セッションが何も痕跡を見ずに同じ作業をやり直したり、逆に
未完成のコードを完成済みと誤認したりするリスクがある。本スキルは、そのずれを機械的に検出し、
安全に復旧してから作業を再開する手順を定める。

## 手順

### 1. ディスク上の実態を確認する(最優先・最も信頼できる情報源)

```
git status
git diff --stat
```

- `git status`の出力そのものが最も信頼できる一次情報。未コミットの変更(`M`)・未追跡ファイル(`??`)を
  すべて洗い出す。これらは「前回セッションが着手し、コミットまで至らなかった作業」の直接的な証拠。
- 変更が広範囲・大量にある場合、`git diff --stat`でファイル単位の変更規模を把握してから個々の
  差分を読む(いきなり`git diff`全体を読むとコンテキストを浪費する)。
- **この時点では絶対に`git reset`/`git checkout --`/`git clean -f`等の破棄系コマンドを使わない**。
  未コミットの変更・未追跡ファイルは前回セッションの成果物である可能性が高く、内容確認前に消すと
  復旧不能になる(git-conventionsスキルの禁止操作にも該当しうる)。

### 2. セッション申し送りドキュメントと突き合わせる

プロジェクトによって置き場所・呼び名が異なるので、まず存在を確認する:

- `docs/handoff.md`、`HANDOFF.md`、`NOTES.md`等(`waterfall-dev-workflow`スキル運用プロジェクトなら
  `docs/handoff.md`・`docs/qa_log.md`が定位置)
- 無ければ`git log`の直近コミットメッセージ、`CLAUDE.md`の「現在の進捗」的な章を代わりに参照する

申し送りドキュメントが見つかったら、**最新の1エントリ**を読み、前回セッションが「何を完了したと
主張しているか」「次回やるべきこととして何を残したか」を把握する。この主張は前回セッションの
自己申告であり、トークン上限で切れた場合はコミット前の主張が記録されただけの可能性がある点に
注意する(=鵜呑みにしない、次のステップで裏取りする)。

### 3. 主張と実態を照合し、内容が本当に完成しているか検証する

手順1(git status)と手順2(申し送りの主張)を突き合わせる。

- 未コミットの変更・未追跡ファイルの集合が、申し送りの「完了した」という主張の範囲とおおむね
  一致するか確認する。
- 一致する場合でも、**該当ファイルを実際に読んで**内容が完成しているか(未完成のTODO、構文エラー、
  尻切れの関数、矛盾した記述がないか)を確認する。git statusに変更が出ていること自体は「完成して
  いること」の証明にはならない。
- プロジェクトにテスト・ビルド等の検証手段があれば、標準の実行コマンド(プロジェクトのCLAUDE.md・
  README等に明記されたもの。独自の一時コマンドは組み立てない)で実行し、現在の状態が壊れていないか
  確認する。既知のflaky事象がある場合(プロジェクトのCLAUDE.md・メモリに記録されていることが多い)、
  それに該当する失敗は単体再実行等で裏取りしてから「既知の環境要因」と結論づける。安易に
  「flakyだろう」と決めつけて調査を打ち切らない。
- 主張と実態が食い違う場合(例: 申し送りは「実装完了」と書いているが該当ファイルが無い/半端な内容)、
  勝手に補完・完成させようとせず、ユーザーに状況を報告して方針を確認する。

### 4. 安全な状態でコミットする

検証の結果、内容が完成していると確認できたら、その時点までの作業をコミットする。

- コミットの粒度・メッセージ規約・push承認の要否は**git-conventionsスキル**に従う(本スキルでは
  重複して定めない)。プロジェクト固有のGit運用ルール(CLAUDE.md記載)があればそちらが優先。
  「作業完了時の自動コミット」の対象になるかはgit-conventionsスキルの当該章を参照する。
- 検証で問題が見つかり修正が必要になった場合は、修正後に改めてコミットする(壊れた状態のまま
  コミットしない)。

### 5. 復旧作業自体を申し送りドキュメントに記録する

セッション申し送りドキュメントがあるプロジェクトでは、「前回セッションが異常終了し、本セッションで
復旧した」という経緯そのものを短く追記する(次回以降のセッションが同じ混乱を繰り返さないため、
また異常終了が繰り返し発生している場合にパターンとして気づけるようにするため)。

### 6. 次の作業を提示する

申し送りドキュメントの「次回セッションでやること」等に記載があればそれを優先度順に提示し、
ユーザーに続行するか区切るか確認する。記載が無い/ドキュメント自体が無いプロジェクトでは、
`git log`・現在のテスト結果・会話に残っている文脈から次の妥当な一歩を提案する。

## 注意事項

- 本スキルはあくまで「状況把握→安全な復旧→再開」のためのものであり、復旧そのものが新しい設計判断や
  スコープ拡大を伴ってはならない。前回セッションが完了させたつもりだった作業をそのまま安全に着地
  させることが目的で、ついでに別の改善を行わない。
- ゲート承認制(`waterfall-dev-workflow`スキル等)を採用しているプロジェクトでは、復旧作業自体は
  通常のドキュメント編集・コミットの範囲に収まる限り都度承認不要だが、`git push`や次工程への
  ゲート承認等、元々承認が必要だった事項は復旧後も引き続き承認を要する(復旧を理由に省略しない)。
