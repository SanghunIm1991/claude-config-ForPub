# 学習用のテキストの書き方

学習用のテキストは、**他の学習者が1人で、先頭から順に読む教科書**として書く。作成を依頼したユーザー本人も、時間が経てば「他の学習者」の1人になる。

- **読者が手元で再現できることを優先する**。読者は、コマンドやサンプルを写して自分の環境で動かす。動かせない読者（読み物として使う人）も、表示と読み方が書いてあれば理解できる。
- **断定する前に確かめる**。サンプルのコード・ツールの挙動・外部ツールの要件は、使い捨ての環境と公式の一次情報で確かめてから書く（[references/verification.md](references/verification.md)）。
- **学習が目的のプロジェクトでは、Claudeはすべてを代行しない**。環境構築と練習はユーザーが行い、Claudeは調査・整理・手順書・一部のサンプルを担う、のように役割を分けることが多い。役割分担はプロジェクトの `CLAUDE.md` に書き、**テキストの本文には書かない**（2節の「教科書の口調」）。

## 1. 書き始める前に決めること

次をユーザーに確認し、決めた内容をプロジェクトの `CLAUDE.md`（書き方の規則）と QA表（qa-log スキル）に残す。途中で変わることも多い（例: 練習用のパスを2回改めた前例）ので、変えたらすべての文書を横展開して直す（4節）。

| 項目 | 決めること | 例 |
|---|---|---|
| 閲覧の形 | GitHub等のWebで読めば足りるか、cloneを前提にするか | Webで読めば足りる → 文書間の参照は相対リンク、clone前提の手順は書かない |
| 読む順番と前提 | 文書の並びと、各文書の前提（どの文書を読み終えていればよいか） | READMEに「読む順番」の表を置き、「前提」の列を設ける。前提に無い文書を当てにしない |
| 練習用のパス | 読者が手を動かす場所 | その分野の公式チュートリアルの慣習に合わせる（教材のフォルダの外） |
| 必須と任意 | 最終目標に必要な範囲と、発展として任意にする範囲 | 任意の範囲を前提にした説明には「作った場合」と注記する |
| 図の形式 | mermaidだけにするか、SVGを本文に表示してmermaid版を添えるか | 基本はmermaid（markdown-mermaid スキルの目安）。SVGを表示してmermaid版を `<details>` に添える形は、レンダラによる表示の違いを避けたい・図を作り込みたい場合にプロジェクトで決める |
| 実行の確認 | Claudeがどこまで実際に動かして確かめるか | ビルド・読み込みまでは確かめ、プロセスの起動は承認を得てから |
| ライセンス | 文章とコードのライセンス、著作権者の表記、第三者の著作物の扱い | 文章はCC BY 4.0、コードはApache-2.0 等。公式の文書の抜粋はユーザーの指示がある場合だけ |

時間のかかる手段（強化学習・長いシミュレーション等）を題材にするなら、書き始める前に、安い予備の実験で「その題材で差が出るか」を確かめる（[references/verification.md](references/verification.md) の5節）。

ユーザー本人の練習環境で気づいたこと（本人のファイルの誤り等）は、テキストに書かず、Git管理外のメモ（例: `notes/practice_notes.md`）に分ける。本人の練習環境はClaudeが直さない。

## 2. 1つの文書の構成と書き方の規則

1つの文書の構成の例:

1. 表題と、冒頭の段落（学習計画のどこに当たるか、何を学ぶか、後でどう使うか）
2. 想定環境・前提・所要の目安・言語（必須か任意か）
3. 注記: このフェーズの位置づけ／進め方（サンプルは読んで理解してから改造してみる、等）／**期待する結果の出どころ**（その文書の表示の出どころだけ。2-2。「期待する結果を載せているので読み物としても読める」のような全体の方針は、READMEに1か所だけ書き、各文書では繰り返さない）
4. `## 0. 学習目標と完了条件`（番号付きで、できるようになることを書く）
5. `## 1. 全体像`（図。3節）
6. 本文の節（仕様 → 主なAPI → サンプル → 解説 → 実行と期待する結果 → 課題）
7. 次の文書へのリンク、出典（参照した公式の文書・ライセンス・逐語の転載でない旨）

書き方の規則の要点（詳細・言い換えの例・理由は [references/writing_rules.md](references/writing_rules.md)）:

- **2-1 教科書の口調**: 「ユーザーが行う」「Claudeは代行しない」「差分を貼ってほしい」のような、役割分担を前提にした言い回しを書かない。
- **2-2 期待する結果**: コマンドやプログラムを実行する手順の直後に、`**期待する結果**` の見出し、表示の例（`text` ブロック）、読み方（どこを見れば成功か）を置く。表示の出どころ（実際に確かめた表示か、仕様から想定した表示か）を文書の冒頭の注記「期待する結果の出どころ」で区別する。全体に共通する方針（読み物としても読めること、実行ごとに変わる部分、実機の表示を優先すること）は、READMEに1か所だけ書く。
- **2-3 必要な情報はその場で**: 先頭から読んだときに理解に要る用語・概念・記号は、その場（同じ節、数十行以内）で示す。初出の用語には1文の定義を置く。注意書きは中身の解説の後に置く。
- **2-4 前方参照は節と中身まで**: 「後述」「④」「課題1」だけで済ませず、「6-2節の④（送信側が `best_effort`、受信側が `reliable`）」のように書く。読み飛ばしても困らない先の案内にだけ使う。
- **2-5 概要は物語調**: 動機づけ・概要の節は、機能の箇条書きでなく、読者が自分の状況に引き寄せて想像できる文章にする（手順の節は表・コード中心のままでよい）。
- **2-6 専門用語の詳細はTips集へ**: 導入で規格の用語や歴史的な比較が続くなら、本質だけを平易に書き、詳細はTips集（例: `docs/tips.md`）へ移してリンクする。
- **2-7 空欄の表を置かない**: 読者が書き込む記録用の表やチェックリストを置かず、著者が確かめた答えを本文に書き切る。
- **2-8 一般論と学習の配慮**: サンプルが一般的な慣習から外れるなら、「一般的な書き方」「このサンプルで変えた理由」「実務での目安」を分けて補足する。一般論の断定は実際のAPIで確かめてから書く。
- **2-9 サンプルのコメント**: クラス・関数ごとに、何をするものかを1〜2行のコメントで書く。本文で行数を比べるときは、そのコメントを除いて数える。
- **2-10 コマンドの書式**: `bash` ブロックには実行するコマンドだけを書き、別のターミナルは `# T1`・`# T2` で区切り、コマンドの間に空行を入れる。出力は常に `text` ブロック。
- **2-11 リンク**: 規約で必要なリンク（次の文書、文中で他の文書を参照するとき、公式の型や仕様の定義）は書く。「あると便利」なだけの相互リンクは、管理の手間が増えるので既定では足さない。
- **2-12 PC固有の情報**: 作成に使ったPCの性能・容量・用途は本文に書かない。見比べる材料として載せるなら、READMEの「確認した環境」の1か所に、ユーザーの判断で載せる。

## 3. 図

- 図の形式は1節の表でプロジェクトごとに決める。基本はmermaidで、mermaidかSVGかの使い分けの目安は markdown-mermaid スキル。SVGを本文に表示する場合は、同じ内容のmermaid版を `<details>` に置く形にできる（GitHubはどちらも表示できる）。
- SVGは手で座標を書かず、生成スクリプト（scratchpadに置く）で作る。箱は格子に並べ、矢印は縦か横の直線だけにする（曲がった線や、箱・文字の上を通る線は読みにくい）。生成スクリプトで、はみ出し・重なり・描画の順を機械的に点検する。レンダラが無い環境での作り方と落とし穴は [references/figures.md](references/figures.md)。目で見られないときは「目視は未確認」と報告し、ユーザーに見た目の確認を頼む。
- 画面のスクリーンショットは図ではないので、mermaid版は置かず、代替テキストと説明の文を添える。撮影はユーザーに頼み（ClaudeはGUIを起動しない）、写り込みとメタデータを確かめてから載せる。

## 4. 書いた後の点検

書いた・直した後は、[references/checklist.md](references/checklist.md) の機械的な点検（grepの例つき）と目視の点検を行う。

- **1件直したら横展開する**: テンプレートや生成スクリプト由来の構造的な不具合は、並行する他の文書にも同じ原因で残っていることが多い。同じパターンをすべての文書で機械的に探してから完了を報告する。
- **方針を変えた後は、前に書いた文書との整合を点検する**: 試行錯誤で題材や構成を作り直したら、前の文書の予告、同じ文書の冒頭の動機づけ、「作成中・暫定」の表示、完了条件と実際の結果、主張の強さ（1回の試行から言い切っていないか）を点検する（checklist.md の3節）。
- **独立したレビュー**: まとまった量を書いたら、文脈を持たないサブエージェントに「他の学習者が1人で先頭から読む教科書として」読ませる（静的レビューのみ・実行しない、と明示する）。

## 5. 権利と公開

- 第三者の著作物（公式の文書・教科書・サンプル・図）は、リンクと自分の言葉による要約に留める。ユーザーの指示で逐語の抜粋をする場合は、ライセンスを確かめ（改変を認めない条件のものはリンクだけにする）、文書の末尾の出典と `LICENSE` の第三者の一覧をそろえる。
- ツールの出力（雛形のファイル・型の定義の表示等）を載せた場合も、出どころとライセンスを出典の注記に書く。
- 公開するリポジトリでは、公開前と更新のたびに public-release-review スキルで点検する。
