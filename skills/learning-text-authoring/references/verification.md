# サンプルとツールの挙動を確かめてから書く

テキストに書くコード・コマンドの挙動・外部ツールの要件は、断定する前に確かめる。確かめられなかったものは、文書の冒頭の注記に「想定」「未確認」と書く。

## 1. サンプルのコード

1. テキストのサンプルに `<!-- file: <練習用のパス>/... -->`（ファイル全体）や `<!-- snippet: 名前 -->`（設定ファイルへの追記分）の印を付けて書く。
2. 使い捨てのスクリプトで印の付いたブロックを取り出し、**scratchpadの使い捨ての作業場所**に置く。抽出スクリプトはリポジトリに置かない。
3. その分野の雛形の作成コマンド → 取り出したコードを重ねる → ビルド、の順に、読者と同じ手順で通す。
4. プロセスを起動せずに確かめられることを先に確かめる: 全モジュールの `import`、エントリポイントの有無、設定ファイルの読み込み（「引数を表示する」「展開した内容を表示する」等のオプション）、登録の確認コマンド。
   - その種のオプションが置換や評価まで行うとは限らない。「展開結果が見える」と書く前に、何が評価されるかを確かめる。
5. プロセスの起動（サーバ・ノード・GUI等）は、プロジェクトの方針でユーザーの承認を得てから行う。承認は、別の質問への回答から推し量らず個別に得て、QA表に独立した行で残す。

起動するときの注意（例はbash。Windowsでは Git Bash やWSLで行うか、同じ目的の方法に置き換える）:

- 他のプロセスと混ざらないように分離する（通信の範囲をローカルに限る環境変数、別の名前空間・ポート等）。
- ログが途中で欠けないように、行バッファにする（`stdbuf -oL -eL`）。`timeout` で止めるとバッファが捨てられることがある。
- 止めるときは `pkill -f` を使わない。パターンが、ユーザーが同じ時間に動かしている同名のプロセスや、ツール自身のシェル（コマンド行にパターンを含む）に一致しうる。バックグラウンドで起動した直後に `$!` でPIDを控え、`kill -INT <PID>` で止める。
- GUIは画面に出さない（オフスクリーンの描画の指定、ヘッドレス・サーバのみのモード等）。それでも画面での確認が要るなら、ユーザーに頼む。
- 壁時計が飛ぶ環境（WSL等）がある。経過時間は単調な時計で測り、ログの時刻の飛びをプロセスの停止と取り違えない。

## 2. ツールの挙動の説明

コードだけでなく、ツールのCLIの挙動（オプションの意味、出力の形、生成されるファイル）も、使い捨ての環境（`git init` した使い捨てのリポジトリ等）で実際に動かしてから書く。

- 前例: ビルドのオプションの効果や、`git status --short` が未追跡のディレクトリをどうまとめて表示するかを、記憶で書いて誤っていた。
- 確かめた表示は、期待する結果にそのまま使える（出どころは「実際に確かめた表示」）。

## 3. 外部ツールの要件・版

- 対応する言語の版・OS・ハードウェア等は、検索結果の要約でなく、**安定版の公式ページ**を直接開いて確かめる。安定版とプレリリース版のどちらの情報かを明記する。
- パッケージの配布元（PyPI等）の情報は、機械的に読める形（PyPIのJSONの `info.version`・`requires_python`・公開日等）で確かめる。
- URLは書く前に実在を確かめる。
- 前例: 検索の要約にあったベータ版の要件を安定版の要件と取り違え、「版が合う」と伝えてしまった（URLも404だった）。

## 4. 使い捨ての環境の扱い

- scratchpadに作る。プロジェクトの練習用の場所（ユーザー本人の作業場所）は使わない・直さない。
- 前回のセッションの使い捨ての環境を再利用するときは、実行前の説明にそのことを書く（`/tmp` 配下は消えていることがある）。
- パッケージの導入が必要になったら、導入先（venv等）を含めてユーザーに確認してから行う。
- **scratchpad（`/tmp` 配下）は、日付が変わったときなどに中身が消えることがある**。数時間かかる計算の結果（学習させたモデル等）のように作り直しが高いものは、ユーザーと決めた消えない置き場所（リポジトリと練習用の場所の外）に置き、できたらすぐ保存先へ写す。使い終わったら、ユーザーに確認して消す。前例: 約1.6時間の学習の結果が日付の変わり目で消え、学習をやり直した。
- **仮想環境（venv）を `cp -a` で写すと、写した側の `bin/activate` と `bin/pip` は元の環境を指したまま**になる（`activate` の中のパスと、`pip` の1行目のインタプリタのパス）。写した側を `activate` してから `pip install` すると、元の環境に入ってしまう。写した側には、`<写し>/bin/python -m pip install ...` で入れ、先に `<写し>/bin/python -c "import sys; print(sys.prefix)"` が写しを指すことを確かめる。ユーザーの環境を変えずに追加のパッケージを試すときに使う。
- **前の実行のプロセスが残っていないかを、計測の前に確かめる**。シミュレータ等が裏に残ると、同じ名前の通信が2つ届き、記録や計測が黙って壊れる（前例: 前の実行のシミュレータが残り、速度のサンプルが約2倍になった）。確かめるときは、自分のシェルに一致しない方法（PIDでの確認、`pgrep` の結果から自分のシェルを除く等）を使う。
- **外部のプロセス（シミュレータ等）とやりとりしながら学習させると、乱数の種を固定しても、実行ごとに結果が変わることがある**（やりとりの時機のわずかな違いが積み重なる）。期待する結果の注記にそのことを書き、同じ設定で2回実行して違いを確かめたなら、その事実も書く。純粋な計算だけの環境なら同じ結果になることも、比べて書いておくと読者が迷わない。

## 5. 題材に差の出る余地があるかを、先に安い方法で確かめる

時間のかかる手段（強化学習・大きな最適化・長いシミュレーション等）を教材の題材にするときは、その手段で書き始める前に、安い予備の実験で「その題材で、比べたいものに差が出るか」を確かめる。

- 「何もしない場合（既定の設定・手で決めた値）」と「最もよい場合の目安（格子の探索など、手段を使わない総当たり）」の差を測る。差が小さければ、手段がうまく働いても、教材として見せられるものが小さい。
- 条件を変えて比べるときは、両端の2条件だけでなく、間の値も含めて測る。両端だけを比べると、差が実際より大きく見える。
- 予備の実験の結果は見通しとして使い、テキストに載せる値は、本番の形で測り直す。
- 前例: 強化学習でゲインを調整する教材を書き上げた後で、既定のゲインがほぼ最良（差が0.07%）と分かり、問題の設定から作り直した。作り直す途中でも、時定数の両端だけを比べて「選び直す価値が大きい」と見誤り、間の値を測って取りやめた。

## 6. 学習者の練習の記録を見るとき

学習者（ユーザー）の練習の出力や作業をレビューする場面がある。

- 練習用のフォルダ（学習者がテキストに沿って作ったファイル）は、レビューのために読んでよい。ただし直さない。
- シェルの履歴（`~/.bash_history` 等）のように、練習と関係のない作業まで残る記録は、**目的と範囲を示して承認を得てから読む**。
  - 履歴には、練習と関係のない作業や秘密情報（コマンドの引数に渡したトークン・パスワード、トークン付きのURL等）が入っていることがある。読んだ内容は、コミットやQA表、サブエージェントへの依頼文に写るおそれがある。
  - 承認を得た後も、必要な行だけに絞って読み（例: `grep` で該当するコマンドの行だけ）、それ以外は出力に出さない。
- 丸ごと読む代わりに、練習用のフォルダのファイルから推定する方法や、必要な部分（例: bashの `history | tail -20`、PowerShellの `Get-History` の出力）を学習者自身が確かめてから貼る方法もある。
- 学習者個人への指摘はテキストに書かず、Git管理外のメモに分ける（SKILL.md 1節）。
