# 書いた後の点検

書いた・直した後に行う点検。機械的な点検は候補を拾うだけなので、ヒットした箇所は目で確かめる。逆に、何もヒットしなくても目視の点検は省かない。

## 1. 機械的な点検（grepの例）

対象のフォルダ（例: `docs/`）に合わせて変える。Windowsでは Git Bash で実行するか、PowerShellの `Select-String` に置き換える。

| 観点 | 探すもの |
|---|---|
| 役割分担の言い回し（2-1） | 「ユーザー」「Claude」「貼ってほしい」「教えてほしい」（伏せ字の `<ユーザー名>` は除く） |
| 期待する結果の見出しの言い換え（2-2） | 「出力例」「期待する結果の例」「期待される結果」 |
| 段落の途中の見出し（2-2） | 行の先頭以外にある `**期待する結果**` |
| 全体の方針の繰り返し（2-2） | 各文書の冒頭の「実行環境が無くても」「期待する結果」として…載せている、のような全文書に共通する文（READMEに1か所だけ書く） |
| bashブロック内の出力のコメント（2-10） | `bash` ブロックの中の `# →`・`# 出力` 等の行（ブロックの開閉を数える小さなスクリプトで探す） |
| 記号だけの前方参照（2-4） | 「後述」、丸数字、「課題」＋数字 → 定義より前の行に出てくるものを確かめる |
| リンクでない文書の参照（2-11） | リンクの中に無い、バッククォートで囲んだ `.md` のパス |
| リンク切れ | 相対リンクの先のファイル・見出しのアンカーが実在するか（小さなスクリプトで確かめる） |
| PC固有の情報（2-12） | 容量（GB・MB）、ユーザー名入りのパス（`/home/`・`C:\Users\`）、ドライブ名 |

```bash
grep -nE 'ユーザー|Claude|貼ってほしい|教えてほしい' docs/*.md | grep -v '<ユーザー名>'

grep -nE '出力例|期待する結果の例|期待される結果' docs/*.md

grep -nE '.+\*\*期待する結果\*\*' docs/*.md

grep -nE '実行環境が(無|な)くても|「期待する結果」として.*(載せている|書いている)' docs/*.md

grep -nE '後述|①|②|③|④|⑤|⑥|⑦|⑧|⑨|⑩|⑪|⑫|⑬|⑭|⑮|⑯|⑰|⑱|⑲|⑳|課題[0-9]' docs/*.md

grep -nE '(^|[^[])`[^`]*\.md`' docs/*.md
```

数式・mermaidの表示の罠の探し方は markdown-mermaid スキルにある。

## 2. 目視の点検

- 先頭から順に読んで、その時点で分からない用語・記号・手順が無いか（2-3）。前提の列に無い文書を当てにしていないか。
- 実行する手順の後に、期待する結果と読み方があるか。冒頭の注記の出どころと、実際の確かめ方が合っているか（2-2）。
- 一般論として断定した文が、実際のAPI・ツールの挙動と合っているか（2-8、verification.md）。
- 概要・動機づけの節が、箇条書きの羅列になっていないか（2-5）。
- 図のmermaid版とSVGの内容が一致しているか（figures.md）。
- 出典の注記と `LICENSE` の第三者の一覧がそろっているか（SKILL.md 5節）。
- 書き方の規則（`CLAUDE.md`）・README（読む順番・確認の状況）・学習計画と、テキストが食い違っていないか。

## 3. 横展開

1件の構造的な不具合（テンプレートの文言、生成スクリプト、書式の誤り）を直したら、その場で「他の文書にも同じ原因で残っていないか」を問い、同じパターンをすべての文書で機械的に探して直してから完了を報告する。指摘を待たない。誤字のような個別の表現まで全件を探す必要はない。

**試行錯誤で方針を変えた後の整合の点検**: 作りながら題材や構成を作り直すと、作り直した文書の中は整っても、前に書いた文書や、同じ文書の別の節に、古い前提が残る。作り直しが一段落したら、次を点検する（前例: 強化学習の文書の作り直しの後、前の章の「〜を扱う予定」、取りやめた題材を前提にした動機づけ、満たしていない完了条件が、複数の文書に残っていた）。

- **前の文書の予告**: 「後の章で〜を扱う予定」「〜で使う」を grep で探し（「予定」「扱う」「後で」等）、実際に扱った内容と合っているか。取りやめた題材の予告は、実際に行ったことに直すか、扱わない理由を添える。
- **同じ文書の冒頭と結論**: 冒頭の動機づけ・全体像と、後の節で書き足した結論（「〜は扱わない」等）が矛盾していないか。後の節だけを直して、冒頭が残ることが多い。
- **状況の表示**: 「作成中」「暫定」「予定」の表示（各文書の冒頭の注記、READMEの表と図、学習計画の状況の表）が、今の状態と合っているか。
- **完了条件・ゴールと、実際の結果**: 計画やアイデアの文書に書いた完了条件・ゴールを、実際の結果が満たしているか。満たしていないなら、条件を直すか、追加で確かめるか、未達と書くかを、ユーザーに決めてもらう（黙って書き換えない）。
- **主張の強さ**: 1回の試行・1回の記録から、一般的な結論として言い切っていないか。比べた相手（既定の値か、調整した値か）と、比べた条件（どの環境・どのシナリオ）を書いているか。両端の2条件だけから一般論にしていないか（verification.md 5節）。
- **ページ番号・節番号の参照**: ページを分けたり繰り上げたりした後、「〜（7-3）」のような番号の参照が、移した先を指しているか。

## 4. 独立したレビュー

まとまった量を書いたら、文脈を持たない新しいサブエージェント（forkでない）に、次を明示して読ませる。

- 立場: 「この分野を初めて学ぶ他の学習者として、先頭から順に1人で読む」
- 範囲: 対象の文書と、前提の文書
- 観点: SKILL.md 2節の規則と、この文書の2節
- **静的レビューのみ（コマンドやコードを実行しない）**
- 報告の形: 重大・中・軽微に分け、場所（ファイルと行）と直し方の案

指摘への対応はユーザーと相談して決め、判断をQA表（qa-log スキル）に残す。
