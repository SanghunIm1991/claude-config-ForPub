# Git運用の汎用ルール

特定プロジェクトの開発フロー（ウォーターフォール等）に依存せず、Claude CodeがGit操作を行う際に常に適用する共通ルール。プロジェクト固有のワークフロースキルを併用している場合、「いつコミットするか」「どの工程で承認を要するか」等の運用面はそちらに従ってよいが、コミット者の識別・メッセージ書式・禁止操作については本スキルを正とする。

## コミット者の識別

Claudeが作成したコミットも、author・committerはユーザー本人とする（GitHubの貢献〈Contributions〉はauthorのメールアドレスで集計されるため。2026-09-23にユーザーの判断で旧規約「author=ClaudeCode」から変更）。Claudeの関与は、メッセージの`[claude]`接頭辞と`Co-Authored-By`トレーラーで示す。

- author / committer: `--author`を指定せず、実行環境のGit設定（`user.name` / `user.email`）をそのまま使う
- Claudeの関与: コミットメッセージ末尾に`Co-Authored-By: <Claudeのモデル名> <noreply@anthropic.com>`トレーラーを付ける（システムから指定される帰属行があればそれに従う）

```
git commit -m "[claude] <要約>" -m "Co-Authored-By: Claude <モデル名> <noreply@anthropic.com>"
```

**コミット前のメールアドレス確認（必須）**: `user.email`はユーザーがGitHubのnoreplyアドレス（`<ID>+<ユーザー名>@users.noreply.github.com`）に設定する運用とする（設定はユーザー自身が行い、Claudeは変更しない）。セッション内で最初にコミットする前に`git config user.email`を確認し、noreplyアドレス以外（個人の実メールアドレス等）だった場合は、コミットせずにユーザーへ報告して判断を仰ぐ。Publicリポジトリでは履歴のメールアドレスを誰でも閲覧でき、履歴の書き換えは禁止操作のため、記録された後では修正できない。

ユーザー自身が手動でコミットする場合は、接頭辞・トレーラーは不要。

旧規約（author=`ClaudeCode <noreply@anthropic.com>`、committerはグローバル設定）で作成済みの過去のコミットは、本規約の変更によって書き換えない（履歴の修正はユーザーが別途判断する）。

## コミットメッセージの書式

- 先頭に `[claude] ` を付け、ユーザー自身の手動コミットと視覚的に区別する。
- 日時をコミットメッセージ本文に個別に書き込む必要はない。通常通り `git commit` を実行すればauthor date/committer dateとして日時が自動的に記録されるため、それで要件を満たす。ただし以下は厳守し、自動記録を骨抜きにしない。
  - `GIT_AUTHOR_DATE` / `GIT_COMMITTER_DATE` 環境変数や `--date` オプションで日時を偽装・上書きしない
  - 変更を溜め込んで後からまとめて1つの巨大コミットにする（バッチコミット）ことは避け、意味のある単位でこまめにコミットする（実際に作業した日時が履歴に残るようにするため）

## 作業完了時の自動コミット

- Claude Codeのデフォルト方針（「明示的な指示がない限りコミットしない」）を、本ルールの範囲内で上書きする。ユーザーから都度の許可を得ずとも、作業が正常に完了したと判断した時点でコミットしてよい。
- 対象はGitで追跡・復元可能な変更（ファイルの編集・追加・削除など）のcommitに限る。push等の復元不能な操作はこの限りでなく、下記の通り別途承認を要する。

## 厳格に禁止する操作（過去のコミットを書き換える・復元不能な操作）

ユーザーの承認有無にかかわらず実行しない（実行してよいか尋ねることもしない）。明示的に依頼された場合も、まず本方針がある旨を伝えて確認を仰ぐ（黙って実行しない・黙って拒否もしない）。

- `git commit --amend`
- `git rebase`（`-i` 含む全般）
- `git filter-branch` / `git filter-repo`
- `git push --force` / `--force-with-lease` / `-f`
- `git reset --hard`
- `git branch -D`（ブランチの強制削除） / `git push --delete`（リモートブランチの削除）
- `git clean -f`（追跡外ファイルの復元不能な削除）
- その他、過去のコミット履歴やリモートの共有履歴を書き換える操作全般

ユーザーから禁止操作を明示的に（繰り返し・「今回に限り」等の限定付きでも）依頼された場合も、承認有無にかかわらず実行しない方針は変わらない。拒否した上で代替手段を提案する際、その代替手段が禁止操作とは異なるコマンドであっても**目的・結果が実質的に同じ**（例: 過去の共有履歴からのデータを完全に消去する等）場合は、それが「禁止操作の代替として、同じ目的を別ルートで達成しようとしている」ものである旨をユーザーへの確認時に明示する。明示せずに提案すると、規約の抜け道と受け取られかねない。

この明示のルールは、代替手段を**提案する**ときのものであり、Claudeが同じ効果の操作を**実行**してよいという許可ではない。禁止操作と結果が実質的に同じになる操作（例: GitHubのブランチ名変更API・Web画面の操作で旧ブランチが無くなる＝リモートブランチの削除と同じ効果）は、Claudeが実行する選択肢として示さず、ユーザー自身が実行する案として示す（手順の案内・前後の確認はClaudeが担当してよい）。2026-10-01、ブランチ名変更（master→main）でAPIによる名前変更をClaudeが実行する選択肢として示し、承認を得て実行してしまった前例がある（実害はなかった）。

過去の履歴から情報を取り除く・author・committer等を修正する必要がある場合は、`git-history-rewrite`スキルに従う（書き換えとforce pushはユーザー自身が実行し、Claudeは調査・フルバックアップ・書き換え用ファイルの作成・検証を担当する。本節の禁止はそのまま維持される）。

技術的にブロックしたい場合は、プロジェクトの `.claude/settings.json` の `permissions.deny` に上記コマンドパターンを登録する（`references/settings_snippet.json` にひな形あり）。`*` はコマンド文字列中の任意位置にマッチするため、`Bash(git push *--force*)` のように対象フラグを `*` で挟むと、引数の並び順（例: `git push origin main --force`）に関わらずブロックできる。

ただし `-uf`（`-u` と `-f` の結合短縮オプション）のように、フォースを含む複数の短縮フラグが1トークンに結合された呼び出しは、パターンマッチだけでは他の正当な引数（ブランチ名など）を誤ってブロックせずに検知することが原理的に難しく、技術的ブロックが効かない場合がある。この残余ギャップは、Claude自身が本方針を理解して実行しないことで担保する。技術的ブロックはあくまで補助であり、方針そのものを厳守する。

## push等、引き続き承認が必要な操作

以下はGitで追跡・復元できない、または外部・共有環境に影響するため、「作業完了時の自動コミット」の対象外とする。

- `git push`
- リモートブランチの作成（削除は「厳格に禁止する操作」節に従い、Claudeは実行しない）
- その他、外部システムへの送信を伴う操作

### push承認の粒度（プロジェクトごとに決定）

上記のうち`git push`について、「commitのたびに毎回pushの可否を確認するか」「コミットとプッシュを1セットの操作として扱い、まとめて承認を得るか」はプロジェクトごとに異なってよい。どちらを採用するかは、そのプロジェクトのCLAUDE.md（プロジェクト固有ワークフロースキルを使う場合はそちらのGit運用ルール節）に明記する。

- **都度確認（デフォルト）**: プロジェクトのCLAUDE.md等に明記が無い場合はこちらを既定とする。commitは自動で行ってよいが、`git push`は実行するたびに個別の承認を得る。
- **コミット+プッシュを1セットで扱う**: ユーザーが「今後はコミットしたらそのままpushしてよい」等、pushの扱いについて明示的に合意した場合に採用できる。この場合、以降のセッションでも改めて確認せずcommitと合わせてpushしてよい。ただし以下は対象外（別ルールとして常に確認・常に禁止のまま）:
  - 「厳格に禁止する操作」節の禁止コマンド（force push・rebase等）は、この運用下でも一切自動実行しない
  - 複数人で共有しているリモート・本番運用中のリポジトリ等、影響範囲が大きい場合は「都度確認」の方が安全であることをユーザーに伝え、判断を仰ぐ

どちらを採用するか不明な場合や、プロジェクトのCLAUDE.mdに記載が無い場合は、ユーザーに確認したうえで決定し、CLAUDE.md側に明記する（次回以降のセッションで同じ確認を繰り返さずに済むようにするため）。

## push拒否時（リモートが先行している場合）の対処

複数端末で開発するプロジェクトで、最新コミットをpullせずに編集し、`git push`が`rejected (fetch first / non-fast-forward)`で失敗した場合の基本戦略。**事前の`git pull`を毎回の習慣にはしない**（発生頻度が低く、pushが拒否されても実害（リモート変更・作業消失）はないため、失敗してから対処すれば足りる）。

1. 未コミットの変更があれば、先にコミットして履歴として保全する（`git stash`は最終手段。pop時の衝突で混乱しやすい）。
2. `git pull --no-rebase`（マージ方式）で取り込む。rebaseは禁止操作のため使わない。
3. 競合したら、内容を読んで手動解消し、`git add`→`git commit`する。どちらを残すか判断できない場合はユーザーに確認する。解消に自信がない場合は`git merge --abort`で取り込み前に戻れる（安全な操作）。
4. 承認を得て、通常の`git push`をやり直す。

`git push --force`・`git rebase`・`git reset --hard`（「ローカルを捨ててリモートに合わせる」目的を含む）は、この場面でも使わない。競合がひどい場合は、ローカルの作業を別ブランチにコミットして退避し、masterをpullしたうえで必要な変更だけ取り込み直す。

`git config pull.rebase false`を1回設定しておくと、`git pull`がrebase方式に流れることを防げる（任意）。
