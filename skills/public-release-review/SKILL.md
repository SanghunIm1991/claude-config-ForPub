# 公開前の点検と事前対応

## 基本方針

- **公開の操作はユーザーが行う**。GitHubのvisibilityの変更、公開用リポジトリの作成・削除は、Claudeは実行しない（手順を案内するだけ）。`git push` は git-conventions スキルとプロジェクトのCLAUDE.mdの承認の粒度に従う（公開前は特に、push前の機密スキャンを省かない）。
- **点検は「今の版」と「全履歴」の両方**を対象にする。今の版を直しても、過去の版（履歴）には元の内容が残る。履歴をどう扱うか（残す・書き換える・1コミットにまとめて新しいリポジトリにする）は、点検の結果を見てユーザーが決める。書き換える場合は git-history-rewrite スキルに従う。
- **機械点検で何も出なくても、目視点検は省かない**。機微な情報の多くは、正規表現で拾えない書き方（一般化した語、経緯の説明、複数の情報の組み合わせ）で残る（下の「見落としやすい場所」と「落とし穴」）。
- **見つけた機微な情報そのものを、会話や記録に繰り返し書かない**。結果は、件数・ファイル名・行番号・コミットIDで伝える。記録（QA表・点検の実施記録）にも、伏せた後の書き方だけを書く。
- **外部への通信は、実行前に目的と影響を説明する**。外部リンクの確認は、対象のドメインの一覧を先に見せ、見慣れないドメインが無いかを確かめてから、HEADの要求（失敗時だけGETで先頭の少量）を送る。PCの情報や非公開のURLは送らない。
- **判断はユーザーに確認する**。点検の後、判断が要る点をまとめてAskUserQuestionで確認する（推奨の選択肢を先頭に置き、理由を添える）。Claudeが独自に判断した点は、記録に「Claude独自判断」と書く（qa-log スキル）。
- 点検の各段階で、承認プロンプトが出やすいコマンド（パイプの多いgrep、スクリプトの実行、外部通信）は、実行前に「目的」と「セキュリティへの影響」を日本語で書く。

## 全体の流れ

| 手順 | 担当 | 内容 |
|---|---|---|
| 0 | Claude→ユーザー | 前提の確認（対象のリポジトリ・ブランチ、公開の形、プロジェクトの点検の文書の有無） |
| 1 | Claude | 機械点検（今の版と全履歴。読み取りのみ） |
| 2 | Claude | 目視点検（見落としやすい場所を読む） |
| 3 | Claude | 権利の点検 |
| 4 | Claude（外部通信はユーザーの承認後） | リンクの点検 |
| 5 | Claude→ユーザー | 結果のまとめと、判断が要る点の確認 |
| 6 | Claude | 修正・記録・コミット |
| 7 | Claude（サブエージェント） | 独立したレビュー（静的な確認のみ。修正のたびに繰り返す） |
| 8 | Claude→ユーザー | push（承認後）と、公開の操作の案内 |
| 9 | Claude（公開後、ユーザーの連絡を受けて） | 公開後の後始末 |

コマンドは `references/commands.md`（bashとPowerShellの両方）、リンクの確認のスクリプトは `references/check_links.py`、プロジェクトに点検の文書を置く場合のひな形は `references/review_doc_template.md` にある。

## 手順0: 前提の確認

- 対象: リポジトリのパス、公開するブランチ（ほかのブランチ・タグ・stashが公開されないか。GitHubはpushしたブランチとタグをすべて公開する）。
- 公開の形: 既存のリポジトリのvisibilityを変えるのか、新しい公開用リポジトリを作るのか。
- プロジェクトに点検の文書（例: `docs/public_release_review.md`）やCLAUDE.mdの「Public化前の棚卸し」の項目があれば、それを読んで、持ち越しの判断事項を洗い出す。無ければ、ひな形から作るかをユーザーに確認する（作らずに、この場の点検だけで済ませてもよい）。
- 使うシェルを確かめる（環境の情報の `Shell:`）。コマンドは、そのシェルの形で使う（`references/commands.md`）。

## 手順1: 機械点検

今の版（`git ls-files`・`git grep`）と、全履歴（`git log --all`・`git log --all -p` の追加行・`git rev-list --all`）の両方に対して行う。

| 観点 | 何を探すか |
|---|---|
| コミットの名義 | author・committerの名前とメールが、公開してよいもの（GitHubのnoreplyアドレス等）だけか |
| メールアドレス | 本文・過去の版に、想定外のアドレス（実メール等）が無いか。noreply・ダミー（`example.com`）・ツールの表記は除外する |
| 認証情報 | APIキー・トークン・パスワード・秘密鍵の形の文字列 |
| ユーザー名・パス | ローカルのユーザー名、ホームのパス（`/home/<名前>`、`C:\Users\<名前>`）、ドライブ文字のパス（実際の保存先を示していないか） |
| アカウント名 | GitHub等のアカウント名（意図して載せる著作権者の表示・リポジトリのURLは除外） |
| PC固有の値 | メモリ・ディスクの容量などの実測値（GB等の数） |
| PCの利用状況 | ユーザーやプロジェクトごとに、機微な用途を示すキーワード。キーワードは、グローバルのCLAUDE.mdやプロジェクトのCLAUDE.mdの機微情報の分類から、ユーザーと相談して決める（キーワードの一覧そのものを、公開する文書やスキルに書かない） |
| 追跡してはいけないもの | 個人メモ・練習用のフォルダ・`.env`・鍵・大きなバイナリ・エクスポート。`.gitignore` と `git ls-files` を突き合わせる |
| 参照 | ブランチ・タグ・stash・過去にだけ存在したファイル |
| コミットメッセージ | `git log --all --format=%B` に、上の観点のものが無いか |

## 手順2: 目視点検（見落としやすい場所）

機械点検では拾えない。次の場所は、必ず読む。

- **記録系の文書**: 判断の記録（QA表）・申し送り・作業ログ。アカウント名、PCの実測値、実際の保存先、個人の練習環境の状態、ツールの内部の呼び名（例: Claudeの作業メモを「メモリ」と書くと、読者はPCのメモリと区別できない）が残りやすい。
- **Claude向けの指示の文書**（CLAUDE.md・AGENTS.md等）: 運用ルール、過去の経緯（履歴の書き換え、旧クローンやバックアップの残作業）、PCの扱いへの注意の言及、「当面private」のような公開後に古くなる記述。
- **企画・アイデアの文書**: PCのスペックの制約、PCの扱いへの注意、個人の別の取り組みへの言及。
- **`.gitignore` のコメント**: 除外している理由の説明に、個人の事情が書かれていないか。
- **環境構築の手順**: 移動先・保存先のパスが、実際の構成を示していないか（例として一般的な書き方になっているか）。
- **組み合わせ**: 1つずつは無害でも、組み合わせると推測できる情報（例: READMEの機種の情報とPCの扱いへの注意の言及、観点の表の一般化した語と「履歴からも消した」という経緯の記録）。
- **画像**: スクリーンショット・写真の写り込み、SVGの埋め込み画像・外部参照・エディタのメタデータ。

## 手順3: 権利の点検

- `LICENSE` があるか。範囲（コードと文章で分ける等）と、第三者の著作物の一覧が最新か。
- 公式ドキュメントの抜粋・引用に、帰属表示（出典・ライセンス・改変の有無）が残っているか。
- 各文書の出典の注記（元にしたもの・ライセンス・逐語の転載でない旨）。注記の文言の揺れ（「出典」「出どころ」「〜に基づく」）で機械点検から漏れることがあるので、注記が無いと出た文書は本文を読んで判断する。
- ツールの出力（型の定義の表示、雛形の各行、警告の文面）を載せている場合、元のパッケージとライセンスを確かめて、一覧と注記に載せる（ライセンスは、インストール済みのパッケージの定義ファイル等で確かめる）。
- 読者に写させる第三者のファイル（リポジトリには含めないもの）の扱いを、`LICENSE` か文書に書いておく。
- 第三者のファイル（PDF・フォント・画像・データシート）が追跡されていないか。依存にコピーレフト（GPL等）のものが加わっていないか。
- **学習済みのモデル（NNの重み等）を配布する場合**:
  - 形式: 読み込むときにコードを実行しうる形式（Pythonのpickle。SB3・PyTorchの `.zip`・`.pt`・`.pkl` 等）は配らない。数の配列だけの形式（numpyの `.npz` を `allow_pickle=False` で読む等）にし、中の各配列の型が数（`<f4` 等）で、オブジェクト（`|O`）でないことを、読み込まずにzipとして確かめる（`references/commands.md` の6節）。
  - ライセンス: 学習に使ったライブラリ・データ・環境のライセンスを確かめ、重みのライセンスの案（例: 学習に使ったライブラリに合わせる）を示して、**ユーザーに決めてもらう**。文章やコードのライセンスをそのまま当てはめて、Claudeが決めない（前例: 文章と同じCC BYを無断で当てはめ、レビューで指摘されて、ユーザーの判断でMITに改めた）。決めたら、`LICENSE` の範囲と全文のファイルを足す。
  - 改行の変換で壊れないよう、`.gitattributes` に `*.npz binary` のように書く。
  - 追跡ファイルの種類の点検（`references/commands.md` の6節の1つ目）の除外に、中身を確かめた重みのファイルだけを名前で足す（拡張子ごと除外しない）。

## 手順4: リンクの点検

- **文書間のリンク**: 相対パスのリンクの先が実在するか（`references/check_links.py internal`）。
- **外部リンク**: まずドメインの一覧を出し（`check_links.py domains`）、ユーザーの承認を得てから確かめる（`check_links.py external`）。
  - ボット対策のあるサイト（例: 公式ドキュメントのサイトの一部。ROS 2 の docs.ros.org など）はツールからの取得に失敗するので、原稿のリポジトリ（GitHub等）の同じパスの有無で代わりに確かめる（`check_links.py` の `--rewrite`）。
  - GitHubの `blob` のリンクは、`raw.githubusercontent.com` の同じパスで確かめる。
  - 名前解決ができない・つながらないものは、一時的な不調か、移転・閉鎖かを見分ける。公式のサイトなら、公式のリポジトリのREADMEが案内している新しいURLに差し替える。非公式の記事は、Web検索で移転先を探し、見つからなければ、同じ趣旨の別の資料があるかを見て外すかを判断する（Claude独自判断として記録する）。

## 手順5: 結果のまとめと確認

結果を「問題なし（機械点検）」「判断が要るもの」「Claudeの判断で進められるもの」に分けて伝え、判断が要るものをAskUserQuestionでまとめて確認する。よく出る問いは次の4つ。

| 問い | 典型的な選択肢 |
|---|---|
| 記録系の文書（QA表・CLAUDE.md・企画の文書）の扱い | 該当箇所だけ直して公開 ／ 公開対象から外す（Git管理外に） ／ そのまま公開 |
| 作成環境に由来する値（ログの時刻、ビルドの秒数、性能の値、READMEの環境の情報） | 機微性が低く学習者・読者の比較材料になるなら残す ／ 一般化する |
| 履歴 | 今の版だけ直して履歴は残す ／ 履歴ごと直す（git-history-rewrite） ／ 1コミットにまとめた新しいリポジトリで公開 |
| 外部リンクの確認 | 確かめる（HEADのみ） ／ 確かめない |

履歴に残るものの機微性が高い（実メール、認証情報、PCの具体的な用途など）場合は、「履歴は残す」を推奨しない。

## 手順6: 修正・記録・コミット

- 決まった方針で直す。過去の記録（QA表の過去の行など）を書き換える場合は、「公開前の棚卸しとしてユーザーが決めた例外」であることを、記録に書く（qa-log スキルの遡及禁止との関係を明示する）。
- 伏せ字は、文書内で統一した形（`<ユーザー名>`・`<ID>` 等）にする。一般化するときは、意味が変わりすぎないか（「ノートPC」を「PC」にする程度か）を確かめ、同じものの表記を文書間でそろえる。
- プロジェクトの点検の文書があれば、実施記録に1行を足す（日付・範囲・結果の要約・対応）。件数など、後で変わる値は「点検した時点の」と書く。
- CLAUDE.md等の「棚卸しの項目」は、決まったことに合わせて、未解決の書き方を残さないように直す（同じ段落に「決める」と「決めた」が並ばないように）。
- 直した後に、手順1の機械点検をもう一度実行する。
- コミットは git-conventions スキルに従う。

## 手順7: 独立したレビュー

会話の履歴を持たない新しいサブエージェントに、静的な確認だけを行うよう明示して、レビューを任せる（review-session の手順）。方針との整合まで見るなら `general-purpose`、危険な操作の検出だけなら `session-safety-reviewer` を使う。プロンプトには次を含める。

- 行ったことの経緯と、ユーザーが決めた方針（残すと決めたものは指摘の対象外）
- 「公開してよい状態か」を最重要の観点とし、今の版と全履歴の両方を見ること
- 手順2の見落としやすい場所と「組み合わせ」の観点
- コマンドの実行・Gitの書き込み・外部通信・他のサブエージェントの呼び出しをしないこと
- 最後に「公開してよいか」の結論を一言で書くこと

指摘への対応は、ユーザーの了承を得てから行う。

## 手順8: push と公開の操作の案内

- push前に、未pushのコミットの名義と追加行を機密スキャンする（git-conventions スキル、グローバルのCLAUDE.md）。
- ユーザーが行う公開の操作を案内する: リポジトリのSettingsで、使わない機能（Wiki・Projects等）を切るかを確かめる → Visibilityを変更する → 公開後に、READMEや図の表示をブラウザで確かめる。
- 旧履歴を含むローカルのバックアップ・クローンの削除は、公開とは別に、ユーザーが確認した後に行う（場所の一覧を公開する文書に書かない）。

## 手順9: 公開後の後始末

- 「当面private」「公開を前提に」のような、公開後に古くなる記述を、公開済みの形に直す（公開の切り替えをユーザーが知らせてから）。
- 以後の運用ルールに、公開後に書いてはいけないもの（アカウント名・PCの実測値・ドライブのパス等を記録に書かない）を加える。

## 落とし穴（実例から）

- **一般化した語でも、経緯の記録と組み合わさると推測できる**。一般化したつもりの語が、まだ元の分野を連想させることがある。別の記録の「具体的に書いてしまい、履歴からも消した」という経緯と組み合わさると、手がかりになる。一般化するときは、分野を連想させない中立な語（「個人の生活を推測させる記述」）を選び、経緯の記録も同じ書き方にそろえる。
- **PCの扱いに特別な注意が要ることを示す言及は、それだけで手がかりになる**。機種の情報（READMEの環境）と並ぶと、狙われやすさを示す。「作業PCのセキュリティに配慮し」のような一般的な書き方にする。
- **棚卸しに回した件の解消が、記録に書かれていない**と、公開後の読者には未解決の懸念に見える。解消したら、元の記録を指して「解消した」と書く。
- **出典の注記の語の揺れ**で、機械点検が「注記なし」と誤る（「〜に基づく」「自分の言葉で書いた」だけの注記）。点検で拾える語（「出典」）を含む1行を足すと、以後の点検が安定する。
- **生成物に、写した元の部品が残る**（例: 別の図の生成スクリプトを写したら、元の図の枠が残った）。文字幅の点検や文法の検証では見つからない。図の中の全文字列を一覧にして、その図のためのものだけかを確かめる。
- **外部リンクの名前解決の失敗**は、公式サイトの移転（例: ドキュメントのドメインの変更）のことがある。公式のリポジトリのREADMEで新しいURLを確かめてから差し替える。
- **点検の結果の件数は、その後のコミットで変わる**（例: コミット数）。実施記録には「点検した時点の」と書く。
- **直した経緯の記録が、直す前の語句を引用してしまう**。「〜という語が手がかりになるので直した」と引用して書くと、直した意味が失われ、かえって目立つ。記録には、直した語句そのものを書かず、「観点の表の語」「PCに関する言及」のように場所と種類だけを書く。
- **PowerShellで日本語が文字化けし、点検が黙って漏れる**。既定の文字コードのままだと、日本語のキーワードで照合しても0件になる。`references/commands.md` の冒頭のとおり、先に文字コードをUTF-8にする。
