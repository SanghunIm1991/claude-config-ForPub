# テストレベルの定義

3階層（単体テスト／結合テスト／統合テスト）で整理する。呼び方はプロジェクトの慣習に合わせてよいが（例: 統合テストを「システムテスト」「総合テスト」「受け入れテスト」と呼ぶ場合がある）、この3層構造そのものは維持する。

## 単体テスト（Unit Test）

- **検証対象**: 個々の関数・メソッドの入出力仕様（挙動）
- **範囲**: 1つの関数・メソッドを、依存先（他クラス・外部I/O）から切り離して検証する。依存先はテストダブル（スタブ・モック・フェイク）に置き換えるか、そもそも依存を持たない純粋な単位を対象にする
- **機能要件の検証**: 通常ケース・境界値・異常値（不正入力・例外）を網羅する
- **非機能要件の検証**: 関数単位で検証可能なものに限る。例:
  - アルゴリズムの計算量・実行時間（パフォーマンスクリティカルな処理）
  - 境界値でのオーバーフロー・精度劣化への耐性
  - 特定の関数に閉じたセキュリティ要件（入力サニタイズ処理など）
- **設計との関係**: ロジックとUI/表示処理・外部I/Oを分離しておくと、この層のテストが書きやすくなる（設計段階からの品質方針として重要）

## 結合テスト（Integration Test）

- **検証対象**: 上位から下位の関数・クラス・コンポーネントを呼び出す経路
- **範囲**: 複数の単体を実際に組み合わせて、インターフェース（呼び出し方・引数・戻り値）とデータの受け渡しが正しく行われるかを検証する。単体テストで個々の正しさは保証済みという前提のもと、「繋いだときに壊れないか」に焦点を当てる
- **機能要件の検証**: コンポーネント間のデータフロー、呼び出し順序、状態遷移
- **非機能要件の検証**: コンポーネント間の結合部分に起因するもの。例:
  - 例外の伝播（下位で発生した例外が上位で正しくハンドリングされるか）
  - リソースの確保・解放（ファイルハンドル、DB接続等）
  - 排他制御・並行アクセス時の整合性
- 外部システム（DB・API等）との結合を含む場合、実物を使うか、テスト用のスタブ環境を使うかをプロジェクトごとに決める（実結合を使う場合は実行速度・再現性とのトレードオフに注意）

## 統合テスト（System / Acceptance Test）

- **検証対象**: 要件定義書に記載された機能要件・非機能要件を、実際のユースケースに沿ってシステム全体として満たしているか
- **範囲**: エンドツーエンドのシナリオ。ユーザー視点での操作フローを通して検証する
- **機能要件の検証**: 要件定義書の各要件ID（例: REQ-xx）に対応するシナリオを用意し、満たしていることを確認する
- **非機能要件の検証**: この層が非機能要件検証の主戦場になる。性能（応答時間・スループット）、可用性、セキュリティ、ユーザビリティ、対応環境（OS・ブラウザ等）など、システム全体でしか測れない特性を扱う
- GUIアプリ等、自動検証が困難な操作を含む場合は `references/regression_and_tooling.md` の「GUIテストの実行主体」を参照

## レベル間の比率（テストピラミッド）の考え方

- 一般的には「単体テストを厚く、統合テストを薄く」（実行速度・安定性・原因特定のしやすさの観点から）が基本方針になる
- ただし、GUIアプリやレガシーコードなど、単体分割が難しい・分割コストが見合わない領域では、結合テスト以上の比率を意図的に上げてよい。その場合は「なぜ単体テストを厚くしなかったか」をテスト仕様書に一言残しておくと、後から方針を見直す際に役立つ
- 比率そのものを数値目標にする必要はない。各レベルが「そのレベルでしか検証できないこと」を担っているかを確認する方が重要（例: 結合テストで検証すべき結合部分の不具合が、単体テストのモック越しに見逃されていないか）
