## 開発プロセス

以下の順に工程を進める。各工程の成果物はユーザーのレビュー・承認を得てから次工程に進むこと（勝手に次工程へ進まない）。

1. 要件定義 (`docs/01_requirements/`)
2. コンポーネント設計 (`docs/02_component_design/`)
3. 関数設計 (`docs/03_function_design/`)
4. 実装 (`src/`)
5. テスト (`docs/04_test/` に仕様書、`tests/` にテストコード)。テストレベル定義・由来管理・リグレッション方針など戦略の詳細は `test-strategy` スキルに従う（「テスト戦略」章参照）
6. デプロイ (`docs/05_deployment/`)

デプロイ工程はプロジェクトの性質によって内容が大きく異なる（スタンドアロンアプリのパッケージング、サーバーアプリのデプロイ、組み込み機器への書き込み、ライブラリ/CLIの公開など）。テスト完了後、着手時点でどのデプロイ形態が適切かをユーザーと合意し、`docs/qa_log.md` に選定理由とともに残すこと（詳細は`waterfall-dev-workflow`スキルの「デプロイ工程」章を参照）。

各工程の成果物には、要件定義書のID（REQ-xx / NFR-xx / CON-xx）を起点としたIDを付与し、`docs/traceability_matrix.md` のトレーサビリティマトリックスに追記すること（詳細は「トレーサビリティマトリックス」章を参照）。

## トレーサビリティマトリックス

要件から実装・テストまでの対応関係を追跡できるよう、`docs/traceability_matrix.md` を工程が進むたびに追記・更新する（工程ごとに別ファイルを作らず、1ファイルで育てていく）。

- 要件↔実装↔テストを1行にまとめた単一表ではなく、**隣接する工程どうしの対応表を4つ**用意する方式とする: ①要件×コンポーネント、②コンポーネント×関数、③関数×テスト、④要件×テスト（直接検証トレース）
  - 理由: 1要件が複数コンポーネント/関数/テストに対応する場合や、逆に1つの関数・テストが複数要件にまたがる場合（多対多）があるため
- 各対応表は、**上流工程のIDを行、下流工程のIDを列に配置したマトリクス形式**とし、関連がある交点に「○」を付ける（多対多の関係を一覧性高く表現するため）
- ③④は関数・テストケースの件数が多くなりやすく列が肥大化するため、列は個々のテストIDではなく**テストモジュール（テストファイル）ID**とし、セルには該当する具体的なテストIDを複数列挙してよい（○ではなくID表記。例: `TEST-03, TEST-07`）
- マトリクスのセルには「○」またはテストIDの列挙のみを記載し、**対応関係の具体的な根拠（なぜ関連するか）はマトリクスに書かず、各工程の成果物（コンポーネント設計書・関数設計書・テスト仕様書）側にID単位で明記する**
- ある行（ID）に対応する列が1つも無い場合（該当する下流要素が存在しない等）は、そのままセルを空欄にしてよい。理由の補足が必要な場合は、表の下に簡潔な注記を添える程度にとどめる
- テスト工程完了時には、「④要件×テスト対応表」の全要件ID（REQ/NFR/CON）の行に最低1つのテストIDが記載されていることを確認し、テストの網羅性チェックとすること
- マトリックスの更新自体は「変更操作の承認について」に従い、通常のドキュメント編集としてその都度の承認確認は不要

### ID対応関係の一次情報源・記載方針（可読性）

要件ID・コンポーネントID・関数ID・テストIDの対応関係を、`docs/traceability_matrix.md` と各成果物本文・テストコードの複数箇所に重複して手で記載すると、一方を直しても他方への反映漏れが構造的に発生し、レビューの往復・トークン消費を押し上げる（自律ループモードで実際に発生した問題。詳細は`waterfall-dev-workflow`スキルの知見を参照）。これを避けるため、以下を徹底する。

- **一次情報源（single source of truth）は `docs/traceability_matrix.md` のみとする**。各工程の成果物本文（コンポーネント設計書・関数設計書・テスト仕様書）には、対応するIDの**簡潔な一覧**（カンマ区切り等）のみを記載してよいが、全IDを毎回フルの理由付きで書き下す必要はない。
- 対応関係が自明でないID（一覧の他のIDと性質が異なる、判断の根拠を残したい等）についてのみ、箇条書きで理由を個別に補足する。「IDを列挙し、1つ1つに逐語的な括弧書き説明を付けて1文に詰め込む」書き方（例:「REQ-01（〜）、REQ-02（〜）、REQ-04（〜）…」と10個以上を1文で羅列する）は避ける。理由を全件均等に書こうとするほど文が密になり、かえって可読性が下がる。
- **テストコード（`tests/`）のdocstring等には、対応するテストID（およびごく短い検証内容の要約）のみを記載し、要件ID・関数IDのフル一覧は重複記載しない**。要件ID・関数IDとテストの対応は `docs/traceability_matrix.md`（および必要ならテスト仕様書側）だけで管理する。
- アーキテクチャ図・データフロー（コンポーネント間の依存関係、処理のシーケンス等）は、複雑になる場合はテキストのみの箇条書き・ASCII表現に頼らず、**Mermaid（`flowchart` / `sequenceDiagram`等）による図示を検討する**。Markdown上でそのまま描画でき、依存の向きや分岐のあるやり取りはテキストの説明より図の方が一読で伝わりやすい。
- 各設計書の冒頭に、版数・作成日・改訂履歴（何を・なぜ変更したか）を記載する「文書情報」表を置くと、レビュー指摘への対応履歴が本文に埋没せず追跡しやすくなる（任意だが推奨）。

## 品質方針（テスト容易性）

開発者によるテスト（主に `tests/` での単体テスト）が行いやすいことを、コンポーネント設計・関数設計の段階から重視する。

- ロジック（盤面状態・手番管理・判定処理など、アプリのドメインに応じて読み替える）とGUI/表示処理を分離し、ロジック層は外部ライブラリに依存せず単体テスト可能な構成にすること
- 関数・メソッドは可能な限り入力と出力（戻り値）が明確な単位に分割し、副作用（画面描画・グローバル状態変更など）とロジックを混在させないこと
- 関数設計書には、各関数の入出力仕様をテストケース設計に転用できる粒度で記載すること
- テスト仕様書（`docs/04_test/`）の各テストケースは、対応する関数設計ID・要件IDとともにトレーサビリティマトリックスに反映すること

## 変更操作の承認について

プロジェクトフォルダ内の変更はGitで追跡・復元可能なため、以下の場合は事前の承認確認を省略してよい。

- 対象: ドキュメント・ソースコードの編集など、Gitで追跡可能な個別のファイル変更操作
- 対象: 上記の変更を確定させる `git commit`（Claude Codeのデフォルト動作は「ユーザーの明示的な指示がない限りコミットしない」だが、本プロジェクトではこれを上書きし、Gitで追跡・復元可能なコミットは都度の承認確認なしに実行してよい。コミットメッセージ規約は「Gitコミット規約」章に従うこと）
- 条件: ユーザーがその場で明示的に承認確認を求めていない場合

ただし、以下は引き続きユーザーの明示的な承認を得てから行うこと（対象外）。

- 「開発プロセス」章に定める各工程間のゲート承認（例: 要件定義→コンポーネント設計への移行など、次工程に進む判断）
- Gitで追跡されない・復元不能な操作（例: `git push`、ファイル削除、外部システムへの送信など）

`git push`を都度確認するか、コミットとセットで（都度確認なしに）扱うかは、プロジェクトごとに決定し明記する（詳細は`git-conventions`スキルの「push承認の粒度」節を参照。未決定の場合は都度確認がデフォルト）。

{{このプロジェクトでのpush運用方針をここに明記する。例: 「本プロジェクトではpushも都度確認とする（デフォルト）」「本プロジェクトではリモートに他の開発者がおらず影響範囲が小さいため、○年○月○日にユーザーと合意の上、コミットとpushをセットで扱う（都度確認不要）」等。ユーザーから方針の指定が無い場合は、着手前に確認してから記入する。}}

### 厳格に禁止するGit操作

以下はユーザーの承認の有無にかかわらず、Claudeは実行しないこと（承認確認をして良いかを尋ねることもしない。ユーザーから明示的に依頼された場合も、まず本方針がある旨を伝えて確認を仰ぐこと）。

- マージ系コマンド（`git merge` など）
- 過去のコミットを書き換えるコマンド（`git commit --amend`、`git rebase`、`git filter-branch`、`git push --force` / `--force-with-lease` / `-f`、`git reset --hard` など）

`.claude/settings.json` の `permissions.deny` にも上記コマンドを登録し、技術的にも実行をブロックしている。`*` はコマンド文字列中の任意の位置（先頭・途中・末尾）にマッチできるため、`Bash(git push *--force*)` のようにフラグを`*`で挟む形にすることで、引数の並び順（例: `git push origin main --force`）に関わらず確実にブロックできる。

ただし、`-uf`（`-u`と`-f`の結合短縮オプション）のように、フォースを含む複数の短縮フラグが1トークンに結合された呼び出しは、パターンマッチだけでは他の正当な引数（ブランチ名など）を誤ってブロックせずに検知することが原理的に難しく、技術的なブロックが効かない場合がある。この残余ギャップは、Claude自身が本方針を理解して実行しないことで担保する（技術的なブロックはあくまで補助であり、方針そのものを厳守すること）。

## プログラム実行の承認について

設計書（コンポーネント設計書・関数設計書）に基づいて作成したプログラム（`src/`の実装コード、`tests/`のテストコード）を、動作確認・レビューのために実行する操作（例: インタプリタでのスクリプト起動、テストランナーの実行）は、以下のいずれにも該当しない限り、都度の承認確認を省略してよい。

- プロジェクトフォルダ外のファイルを書き換える場合（設計上想定されていない副作用であり、Gitで追跡・復元できないため）
- 本章より下で、特定の実行操作について承認を要する旨が明記されている場合

{{実装工程着手時に、実際に使用する実行コマンド（例: `py -3.13 *`、`py -3.13 -m pytest *`、プロジェクト専用venvなら `.venv\Scripts\python -m pytest *` など、言語・ランタイムに応じて具体化する）を`.claude/settings.json`の`permissions.allow`に追加し、ここにも明記する。許可リストに追加してもなお、ツール権限の仕組み上どうしても確認が求められる場合は、実行のたびに都度確認するのではなく、当該工程（実装・テスト）着手前の計画段階でまとめて承認を得ておくこと。}}

### テスト実行コマンドの標準化（承認プロンプト削減）

開発・レビューサブエージェントが呼び出しごとに異なる形のワンライナー（作業ディレクトリを変えてから`&&`で連結する、シェルの`for`/`foreach`ループで複数回実行する、ランタイムの絶対パスを直接指定する等）を作ると、`permissions.allow`のパターンに一致せずその都度承認が必要になりやすい。これを避けるため、以下を徹底する。

- テスト実行は言語・ランタイムに応じた少数の標準形のみを使う（ランタイムのバージョン管理コマンド・ランチャー、またはプロジェクト専用venvの相対パスを使い、絶対パスを直接指定しない。ランチャーで呼べないランタイムは、グローバルCLAUDE.mdの「Python環境」節に従い、毎回同じ形で呼ぶ。「実装環境」章参照）
- テストの入出力はテキスト形式（標準出力への通常のテストランナーのレポート）に統一し、判定は終了コード・テキストレポートのみで行う。バイナリ出力の比較やGUIスクリーンショットを用いた検証は避ける
- 同一テストを繰り返し実行してflaky挙動を確認する必要がある場合も、シェルのループで包まず、標準形をそのまま複数回呼び出す（1呼び出し1コマンド）か、テストランナー側のリピート機能（例: pytestなら`pytest-repeat`）を使う
- サブエージェントには前提の作業ディレクトリを伝え、`cd`を伴う複合コマンドを極力使わせない。やむを得ず使う場合は`cd * && <実行コマンド> *`のような単純な形に留め、該当パターンを`permissions.allow`に追加する（既に実行コマンド自体が無条件許可済みであれば、`cd`を挟んでも実質的な権限拡大にはならない）

## セッション運用方針

各セッションでの作業の進め方について、以下のフローに従うこと。

1. **即時着手**: ユーザーから指示を受けたら、作業概要の提示や承認を待たず、プロジェクト内のファイル作成・編集にすぐ着手してよい（「変更操作の承認について」章の方針の通り、個別の承認確認は不要）。ただし、開発プロセスの工程間ゲート承認など、同章で明示的承認が必要とされる事項はこの限りでない。
2. **完了時の挙動**: 指示された作業が正常に完了した場合は、完了報告を行った上で待機する（対話セッションを自らの判断で強制終了することはしない）。
3. **申し送り**: 工程間ゲート承認など、ユーザーの明示的承認が必要な事項が残っている場合は、その旨をユーザーに提示するとともに、`docs/handoff.md` に次回セッションへの申し送り事項を記録する。
