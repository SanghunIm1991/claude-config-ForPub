# レビュー観点（自律ループモード用）

自律ループモードのレビューサブエージェントが各工程の成果物をレビューする際に使う観点集。工程ごとに、ここに挙げる観点で指摘の有無を判定する。指摘は些細なものでも省略せず全て挙げること（黙って見逃さない、という意味であり、後述の通り書き方まで1件1件冗長にする必要はない）。

ただし、同種の軽微な指摘（特に「重大／軽微の判定」章の例外に該当するID転記漏れ等）が多数見つかった場合は、1件ごとに独立した行として詳述せず、「〇〇系のID転記漏れがX件（対象: …）」のようにまとめて1件として報告してよい。これは指摘を握りつぶすことではなく、往復・トークン消費の削減（`waterfall-dev-workflow`スキルの知見）と、指摘の一覧性を両立するための書き方の工夫である。内容面の矛盾を伴う指摘（重大判定）は引き続き個別に詳述すること。

## 重大／軽微の判定

指摘は1件ごとに、レビューサブエージェント自身が**重大**または**軽微**をタグ付けして報告すること（オーケストレーターに後から判定させない。オーケストレーターは工程を前に進めたい構造的な動機を持つため、後付け判定だと軽微側に倒れるバイアスがかかりうる。判定の独立性を保つため、判定自体を独立したレビューサブエージェントの成果物の一部として確定させる）。

- **重大**: 内容面の矛盾・欠落、確定仕様との不整合、上流工程IDとの対応関係の欠落・誤り、動作しない／誤った結果を返すコードなど、確信度が高いもの
- **軽微**: 誤字脱字・表記揺れ、曖昧表現の指摘など内容面の矛盾に至らないもの、確信度が中〜低のもの（「〜の可能性がある」程度の指摘）

判断に迷う指摘は軽微側に倒さず重大側に倒す（品質を優先する）。

ただし例外として、**IDの記載漏れ・転記漏れであって、内容面の矛盾（異なるIDが対応付けられている、範囲の解釈が食い違う等）を伴わないもの**（例: `docs/traceability_matrix.md`のセルと成果物本文のID一覧が単純に同期していないだけで、どちらの記載を正としても実質的な解釈のズレが生じない場合）は、原則として軽微に固定する。これは「迷えば重大」の原則より優先する。理由: この種の指摘は自律ループモードで往復・トークン消費の大半を占めることが実績として分かっており（`waterfall-dev-workflow`スキルの知見）、「ID対応関係の一次情報源・記載方針」（`claude_md_template.md`参照）に沿って一次情報源を`docs/traceability_matrix.md`に一本化していれば本来発生しにくい種類の指摘でもあるため、内容面の矛盾に至らない限り再レビューを強制しない。

## コンポーネント設計・関数設計における論理/可読性レビューの分離

この2工程は開発・レビューを論理面と可読性面の2段階に分ける（`loop_mode.md`「設計工程の論理/可読性2段階パイプライン」章参照）。以下は本rubric内の各観点をどちらのレビュー呼び出しで使うかの割り振り。

- **論理レビューサブエージェント**が確認するもの: 「共通観点（全工程）」のうち「可読性」「図解」「誤字脱字・表記揺れ」の3項目を**除いた**全項目、および「コンポーネント設計」「関数設計」章の項目全て。文章表現の巧拙は指摘しない（後段の可読性フェーズの担当であり、論理面のラウンドで指摘しても手戻りになるだけ）。
- **可読性レビューサブエージェント**が確認するもの: 「共通観点（全工程）」の「可読性」「図解」「誤字脱字・表記揺れ」の3項目、および次の**意味的ドリフト**の確認。
  - 可読性向上サブエージェントによる修正の前後（論理面確定版 vs 可読性向上後版）を比較し、対応要件ID・対応コンポーネントID・数値・判断内容などの**内容面が変わっていないか**を確認する。文章構成・表現・見出し・図解以外の変更（意味が変わる言い換え、条件の追加・削除、ID対応関係の変化など）が見つかった場合は指摘とする。
  - 意味的ドリフトの指摘は「重大／軽微の判定」章の基準にかかわらず**常に重大**として扱う（内容が意図せず変わることは、たとえ小さな言い換えでも見過ごせないため）。

## 共通観点（全工程）

- 誤字脱字・表記揺れ
- 上流工程のIDとの対応関係が明記され、**内容面で**矛盾がないか（IDの単純な転記漏れそのものは「重大／軽微の判定」章の例外に従い軽微。ここで見るのは対応関係の実質的な誤り・矛盾）
- 曖昧な表現（「適宜」「必要に応じて」など、後工程で解釈が割れる余地のある記述）がないか
- 該当するIDが `docs/traceability_matrix.md` に反映されているか（反映漏れも指摘対象とするが、`claude_md_template.md`「ID対応関係の一次情報源・記載方針」に沿い一次情報源をマトリクスに一本化できていれば本来起きにくい種類の指摘であることを踏まえ、内容面の矛盾がない限り軽微とする）
- 題材について一般的に知られた実世界の慣習・前提（既存のゲームの通例、業界標準的なUI/UX等）と、成果物の記述内容がズレていないか
- 新設・変更したID（REQ/NFR/CON等）について、下流工程（設計書・トレーサビリティマトリックス）での説明・注釈が、上流の確定文言（要件本文等）が実際に定める範囲を超えて、他の設計判断まで拡大解釈されていないか（IDの説明範囲のスコープクリープ。例: 視認性のみを規定するNFRの説明に、別の要件が根拠であるはずの配置・配色以外の設計判断が紛れ込んでいないか）
- **可読性**: 対応要件ID等の一覧が、読み手が一読して把握できる形式で提示されているか。全IDを1文の中に均等に列挙し、1つずつ逐語的な括弧書き説明を詰め込んでいないか（`claude_md_template.md`の記載方針に沿い、簡潔なID一覧＋非自明なものだけの個別説明になっているか）
- **図解**: 複数コンポーネントにまたがる依存関係や処理のシーケンスなど、テキストの箇条書き・ASCII表現よりMermaid等の図の方が伝わりやすい内容を、図示せず文章のみで済ませていないか

## 要件定義 (REQ / NFR / CON)

- 要件間の矛盾・重複がないか
- 実現不可能・技術的に矛盾した要件がないか
- 非機能要件（NFR）・制約（CON）が機能要件（REQ）と混同されていないか
- 各要件にIDが採番され一意か
- GUIを持つ題材の場合、配色・視認性など見た目に関わる非機能要件の要否が検討されているか（検討した結果「不要」と判断したのであれば良いが、検討した形跡自体が欠落していないか）

## コンポーネント設計

- 全要件（REQ/NFR/CON）が最低1つのコンポーネントに対応しているか
- コンポーネント間の責務分担が重複・欠落していないか
- ロジック層とGUI/表示層の分離方針（品質方針）に沿っているか
- コンポーネント間の依存関係・データフローが、テキストのみ（ASCII図・箇条書き）で表現され、Mermaidの`flowchart`/`sequenceDiagram`等で図示する余地を逃していないか
- **排他制御・ロックの完全性**: 排他制御・ロック・アトミック操作を新設または変更している場合、(a) チェックと更新（check-then-act）が分離されておらずレース条件が生じないか、(b) クリティカルセクション内のあらゆる早期リターン・例外経路でロック解放が保証されているか（個別パターンの列挙ではなくtry/finally等による一律カバーになっているか）、(c) 関連する状態フラグの読み書きが同一のロックで一貫して保護されているか、を確認する（同種の指摘が複数コンポーネントにまたがり繰り返し発生し再レビュー上限到達に至った実績があるため、この観点は独立した確認項目として明示する）

## 関数設計

- 各関数の入出力仕様が、そのままテストケース設計に転用できる粒度で書かれているか
- 副作用（画面描画・グローバル状態変更など）とロジックが混在していないか
- 対応するコンポーネントIDとの整合性

## 実装

- 関数設計書との整合性（シグネチャ・入出力・副作用の有無）
- ロジック層が外部ライブラリ（GUIなど）に依存していないか（品質方針）
- 明らかなバグ・例外処理漏れ
- 視覚的な表現（座標計算・配色など）について、意図した見た目と実装が一致しているか。特に背景色と描画物の色が衝突して視認できなくなる組み合わせが存在しないか
- GUIコンポーネントの場合、正常系の画面遷移をたどる最小限のUI操作（クリック・入力等）でスクリーンショットを取得し、意図した見た目になっているか目視確認したか（異常系の検証や網羅的な自動操作は対象外。想定と異なる場合はUI操作を打ち切り静的な方法で原因究明する）
- **実行確認を必須とする**: 静的な読解だけで済ませず、実際に起動して（例: `py -3.13 src\main.py` など、CLAUDE.mdの「実装環境」章に従う）エラーなく動作することを確認する。起動確認をしていない場合、その旨を指摘として報告する（起動確認の省略自体を軽微指摘として扱う）

## テスト

- 全要件ID（REQ/NFR/CON）の行に最低1つのテストIDが対応しているか（網羅性）
- テストが該当する関数設計・要件を実際に検証する内容になっているか
- 異常系（境界値・不正入力など）が正常系だけでなく含まれているか
- 各テストケースに**テストレベル**（単体/結合/統合）と**由来**（仕様/設計ベース・コードベース・レビュー指摘ベース）が明記されているか（`test-strategy`スキル参照）。由来が「仕様/設計ベース」なのにトレーサビリティマトリックスに反映されていない、逆に「コードベース」なのに対応要件IDが無理にこじつけられている、といった不整合がないか
- テストコード（`tests/`）のdocstring等が、テストIDとごく短い検証内容の要約に留まっているか。要件ID・関数IDのフル一覧を重複記載していないか（`claude_md_template.md`「ID対応関係の一次情報源・記載方針」参照。違反していても内容面の矛盾でなければ軽微指摘とする）
- リグレッション方針（フル/代表ケース）がCLAUDE.mdまたはテスト仕様書に明記されているか。代表ケースリグレッションを採用している場合、テスト仕様書上の代表ケース指定と `tests/` 側のテストコードのマーカー・タグが一致しているか
- テスト入力データが複雑な場合に外部ファイル（テキスト/CSV/JSON）へ切り出されているか、バイナリデータを使う場合はユーザーの明示的指定によるものか（`test-strategy`スキル参照）
- マウス・キーボード操作を伴うGUIテストのケースが、AIエージェントによる操作自動化を前提とせず、実行手順の記載にとどめてユーザーによる手動実行を前提にしているか
- **実行確認を必須とする**: テストコードを実際に実行し（例: `py -3.13 -m pytest tests\`）、全件パスすることを確認する。実行せずにコードの読解だけでレビューを終えない。失敗したテストがあれば重大指摘として報告する

## デプロイ

デプロイ形態（スタンドアロンアプリ／サーバーアプリ／組み込み等）によって内容は異なるが、共通して以下を確認する。

- マニュアルに記載されたビルド/デプロイ手順（コマンド等）が、実際のビルド設定ファイル（`.spec`ファイル、`Dockerfile`、CI設定等）の内容と整合しているか
- 配布・デプロイ先の動作環境・実行手順の説明が、成果物を受け取る側（想定読者）にとって過不足なく分かりやすいか
- 既知の注意事項・トラブルシューティングが、実際にビルド・デプロイ時に遭遇した問題（`docs/qa_log.md`参照）を反映しているか
- ビルド生成物（実行ファイル・コンテナイメージ等）のうち、Gitで管理すべきもの（設定ファイル等）と管理すべきでないもの（バイナリ本体等、`.gitignore`で除外）が適切に切り分けられているか
- **実行確認を必須とする、ただし範囲を限定する**: 実際にビルド・デプロイ済みの成果物を起動・デプロイし、起動直後にクラッシュしないか、異常なエラー出力がないかを確認する（スモークテストで十分）。GUIアプリの場合は、正常系の各画面へ遷移する最小限のUI操作（クリック・入力等）を行い、到達した画面をスクリーンショットで目視確認することも確認範囲に含める。**ただし異常系（エラーケース・境界値等）の検証や、クリック操作の網羅的自動再現・スクリーンショット比較等の厳密なUI自動検証は試みないこと**（検証手段を模索し続けて長時間・大量のツール呼び出しに陥る「暴走」のリスクがあるため）。想定した挙動と異なる結果になった場合は、その時点でUI操作による確認を打ち切り、原因究明は静的な方法（コード読解等）に切り替えること（原因が分かるまでUI操作で探り続けない）。詳細な機能レベルの動作確認は人間による手動確認に委ね、その旨をレビュー結果に明記する
- **起動確認は標準出力/エラー出力を捕捉した上で判定する**: プロセスが存在する（生存している）ことの確認だけでは不十分。GUIアプリを非同期に起動して直後にプロセス一覧を確認する方法だと、起動直後にクラッシュしていても一瞬プロセスが見えたり、ウィンドウなしアプリ（コンソール非表示ビルド等）のエラー出力が握りつぶされて「異常なし」と誤判定する場合がある。成果物を直接実行し標準出力・標準エラーをリダイレクトして内容を確認する、またはコンソール出力ありビルドで一時的に検証するなど、エラーテキストを実際に読める形で起動確認を行うこと
