アイデア用の別のリポジトリで育てたアイデアを、このプロジェクトで実現します。元アイデアは `docs/idea_origin.md` にあります。次の順で進めます。

## 進め方の共通ルール

- 段階1は要約後にそのまま段階2へ進んでよい。段階2以降は、各段階の終わりでユーザーの確認を取り、確認前に次へ進まない。
- Claudeが質問・提案を行い、ユーザーが判断した内容は、`qa-log`スキルに従って `docs/qa_log.md`（QA表）にその都度記録する（`docs/qa_log.md` が無ければ最初の判断時に新規作成する）。質問はAskUserQuestionを使い、推奨案を添えて選択肢を出す。工程列には段階名（「Git環境」「ツール確認」「直近ゴール」等）を書く。
- ルール（セキュリティ・コミット規約・著作権・Python環境等）は `~/.claude/CLAUDE.md` と本プロジェクトの `CLAUDE.md` に従う。ここでは繰り返さない。

## 1. アイデアの理解

`docs/idea_origin.md` を読み、目的・決定済みの事項・案・未決事項を短く要約する。元アイデアは別のリポジトリから写したものなので、PCの環境・利用状況を推測させる記述（PCのスペックの制約等）が残っていないかも確かめ、あればユーザーに伝える。要約でClaudeが解釈した点や、不明で確認したい点があればここで質問し、回答をQA表に記録する。

## 2. Git環境の構築

現状（gitリポジトリか、ユーザー設定、`.gitignore`、リモートの有無と公開範囲）を確認し、不足があれば整える案を示す。実施はユーザーの承認後。

- ローカルの `git init` と `.gitignore` の作成は、案を承認した後に実施する。
- git のユーザー設定などの設定変更は、内容を示して承認を得る。
- GitHub上のリポジトリ作成・push・公開範囲の変更など、外部に影響する操作は、実行前に内容を示して承認を得る。
- リポジトリは、公開（public）できる状態を前提に作る。これは必ず守る。
  - GitHub のリポジトリは private で作る。public に切り替えるかは、ユーザーがあとで判断する（公開の操作はユーザーが行う）。
  - 機密情報・個人情報・第三者の著作物を、追跡するファイルにもコミットの author・committer 欄にも入れない。手元にだけ置くものは `.gitignore` で除外する。
  - push の前の点検は、`public-release-review` スキルの手順1（機械点検）と手順2（目視点検）の観点に従う。QA表などの記録の文書とコミットメッセージも対象にする。
  - この方針を、本プロジェクトの `CLAUDE.md` にも書く（次のセッション以降も守られるようにするため）。
- リポジトリ名・`.gitignore`の方針・コミット規約の確認（`git-conventions` スキル参照）など、ユーザーが判断した内容はQA表に記録する。

## 3. インストール済みツールの確認

ソフトウェアやツールを要しないアイデアであれば、その旨を述べてこの段階を省略する。

要する場合は、元アイデアの記述に挙がっている、または記述から明らかに必要なツール・ランタイム・SDK に限り、このPCに入っているかを突き合わせ、「導入済み／不足」の一覧を作る。記述にないものを推測で加えない。

- 確認は、対象ツールそれぞれの `--version` 実行や PATH 上の存在確認に限る。
- 環境変数・設定ファイル・認証情報の内容は開かず、PC全体のソフト一覧も取得しない。
- インストールや設定変更はしない。不足分は手順の案を示すにとどめ、導入の要否・方法（Pythonパッケージなら共有anaconda環境かプロジェクト専用venvか等）はユーザーに確認して、判断をQA表に記録する。

## 4. 直近のゴール設定

ここまでを踏まえ、最初に到達する直近のゴール（規模の目安と完了の判定基準つき）を提案する。ゴール案が複数ある場合は選択肢と推奨案を示して確認する。承認された内容と、その理由をQA表に記録した上で、作業計画に進む。
