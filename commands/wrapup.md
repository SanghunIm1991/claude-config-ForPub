---
description: セッションを閉じる前に、必要な情報を整理してコミットする
---

セッションを閉じます。以下を順に行ってください。

1. このセッション中にバックグラウンドで起動したエージェント・タスク（Agent/forkツール、Monitor、run_in_background等）がないか確認する。何も起動していなければこの手順は不要。
   - 起動したものがあれば、完了済みか実行中か確認する（block=falseでのTaskOutput確認等、待機せず状態だけ見る）。
   - 実行中かつその成果物がこのセッションの完了報告やコミット内容に必要な場合は、クローズせず完了を待つかユーザーに確認する。
   - 実行中でも単なる下調べ・補助的な調査で、結果を使わない/使い終えている場合はクローズして問題ない。
   - 迷う場合はクローズ可否をユーザーに確認してから進める。
2. `git status` / `git diff` で、このセッション中に生じた変更（未コミット分）を確認する。
3. コミットのルール（コミッター名・メッセージ書式・禁止操作）は `git-conventions` スキルに従う。プロジェクト固有のワークフロースキル（例: waterfall-dev-workflow）がある場合はそちらのGit運用ルールも合わせて確認する。push の扱いはこのコマンド固有の方針として下記8を参照（`git-conventions` の既定「都度承認」を、`/wrapup` に限り2026-08-22のユーザー合意により上書きする）。
4. プロジェクトに進捗・状態を記録する場所がある場合（README の「現在の状態/次のステップ」、waterfall-dev-workflow のセッション申し送りファイルなど）、既存の書式に合わせて今回の変更点・次にやることを簡潔に更新する。存在しない場合は無理に新設しない。
5. 意味のある単位で変更をステージングし、コミットする。無関係な変更を1つの巨大コミットにまとめない。
6. 自動生成物・キャッシュ等コミット対象外のファイルが混ざっていないか確認する（`.gitignore` の見直しが必要ならその場で行う）。
7. 今回の会話で得られた知見のうち、今後のセッションでも役立つ非自明な情報（ユーザーの好み・プロジェクトの背景・ハマった落とし穴など）があれば、auto memory の仕組みで該当する種類（user/feedback/project/reference）に保存する。ソースコードから読み取れる内容や、すでにメモリ・CLAUDE.mdにある内容は保存しない。
8. コミット後、禁止されていない限り `git push` まで実行する（ユーザーが2026-08-22に「`/wrapup` ではコミット+プッシュを1セットで扱ってよい」と明示的に合意済み）。ただし以下のいずれかに該当する場合は push せず、可否をユーザーに確認する。
   - プロジェクトのCLAUDE.md（またはプロジェクト固有ワークフロースキルのGit運用ルール節）に「push は都度確認」など異なる方針が明記されている場合は、そちらを優先する
   - 複数人で共有しているリモート・本番運用中のリポジトリなど、影響範囲が大きいと判断される場合（`git-conventions` スキル参照）
   - 通常の fast-forward push では完結しない状況（リモートに未取得のコミットがある等、`git push --force` 系の操作が必要になる場合）— この場合は `git-conventions` スキルの禁止操作に該当するため、そもそも実行しない
   - ユーザーから今回は push しないよう明示的に指示されている場合
9. 最後に、コミットした内容・保留した点・次回再開時にまず確認すべきことを3〜5行程度で簡潔にまとめて報告する。
